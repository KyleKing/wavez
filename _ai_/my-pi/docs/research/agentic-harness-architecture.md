# Agentic coding harness architecture (August 2026)

Research pass across Claude Code, OpenCode, Aider, Cline, Goose, and Continue, using official docs, GitHub source, and engineering posts current as of 2026-08-12. Continue's repo went read-only after Cursor's acquisition (final release `2.0.0` on 2026-06-19, cloud data deleted after 2026-07-15, per the repo's own banner; acquisition details corroborated by [The New Stack](https://thenewstack.io/cursor-acquires-continue-coding/) but not an official post — unverified beyond the repo banner). Everything below on Continue describes its architecture as last actively developed, now frozen.

Claims marked **[unverified]** could not be pinned to a primary source in this pass. Where two sources disagreed, both are named.

## 1. Core tool-use loop and context management

### The loop itself

Claude Code frames itself explicitly as a harness around the model, not the model itself: "Claude Code serves as the agentic harness around Claude: it provides the tools, context management, and execution environment" ([code.claude.com/docs/en/how-claude-code-works](https://code.claude.com/docs/en/how-claude-code-works)). The documented cycle is gather context → take action → verify results → repeat, the same shape across terminal, IDE, claude.ai, and CI. It's streaming-first: tool calls start executing mid-stream, and a user interrupt is read in as soon as the current action finishes. A reverse-engineering paper (arXiv:2604.14228v1, "Dive into Claude Code," 2026-04-14, analyzing v2.1.88's TypeScript source) names an async `queryLoop()`, an internal "nO" master loop over a single flat message thread, and a `StreamingToolExecutor` that runs read-only tools concurrently while serializing state-mutating ones like Bash — unverified against Anthropic itself, since it comes from third-party reverse engineering of the shipped binary.

OpenCode splits client from server: a Bun/Hono HTTP server does the work and streams updates over SSE, while the Go/Bubble Tea TUI is a pure client talking to `/prompt_async` and `/event` ([opencode.ai/docs/server/](https://opencode.ai/docs/server/)). A community deep-dive (cefboud.com, 2025-09-14, secondary source) says it's built on the Vercel AI SDK's `streamText`, consuming `tool-call`/`tool-result`/`tool-error`/`text-delta` stream events and terminating on `stopWhen` conditions rather than "no more tool calls." This is the most protocol-abstracted of the six — a headless server with an OpenAPI 3.1 spec that the TUI is just one client of.

Aider is turn-based underneath its streaming terminal output: `Coder.send_message()` assembles system prompt, repo map, files, and history; streams the raw completion to the terminal; and only after the full response lands does `apply_updates()` parse SEARCH/REPLACE edit blocks out of the finished text (read directly from `aider/coders/base_coder.py`; corroborated by techramblings.blog, 2025-07-19). Lint and test failures re-enter as the next turn through `self.reflected_message`, not a distinct tool-result channel. Its Architect/Editor mode ([aider.chat/2024/09/26/architect.html](https://aider.chat/2024/09/26/architect.html), 2024-09-26) splits reasoning and edit-formatting into two separate inference calls, optionally two different models.

Cline streams at the tool-call level genuinely, not just at the terminal: a `presentAssistantMessageLocked` flag and streaming content pointer let tool calls begin executing while later parts of the same model turn are still arriving ([cline/prompts .clinerules/cline-architecture.md](https://github.com/cline/prompts/blob/main/.clinerules/cline-architecture.md), official, in-repo). Tool calls are XML-tag formatted, gated by approval, and results return as the next API turn. The architecture is three layers (Core Extension ↔ WebviewProvider ↔ Webview UI, via gRPC) behind a `HostProvider` abstraction so the same `Task` core runs across VS Code, JetBrains, and CLI.

Goose names its loop explicitly: Build Context → Model Invocation → Stream Processing → Tool Execution → Continue Loop (block-goose.mintlify.app/concepts/agents, fetched 2026-08-12). A `PromptManager` assembles system prompt, history, and tools; requests stream; completed tool-call chunks run a permission check then dispatch via `ExtensionManager.call_tool()`. The loop caps at `GOOSE_MAX_TURNS` (default 1000). Function/class names come from Mintlify docs and DeepWiki, not a direct read of the Rust source — unverified at that level of detail.

Continue's CLI (`cn`) builds on a `ServiceContainer` dependency-injection pattern (auth → apiClient → agentFile → config → model → chatHistory), per [DeepWiki's CLI architecture page](https://deepwiki.com/continuedev/continue/10.1-cli-architecture-and-commands) — an AI-generated documentation source, so treat it as secondary. Whether the model-tool exchange itself streams or is turn-based is unverified; even DeepWiki's own page doesn't fully resolve it.

### Compaction and long-session handling

Claude Code documents this in the most detail of any tool researched. Context is managed automatically as the limit approaches: older tool outputs clear first, then the conversation summarizes if needed ([code.claude.com/docs/en/context-window](https://code.claude.com/docs/en/context-window)). Auto-compact is on by default with a model-dependent threshold, adjustable via `/autocompact <token count>`; `/compact <instructions>` or a persistent Compact Instructions block in CLAUDE.md steers what survives. A documented survival table: the system prompt and project-root CLAUDE.md/auto-memory get re-injected from disk after compaction; path-scoped and nested CLAUDE.md rules are lost until re-triggered; skill bodies re-inject capped at 5,000 tokens each, 25,000 total. A thrashing guard stops retrying compaction if context immediately refills. Windows run up to 1M tokens on Sonnet 5, Fable 5, Opus 4.6+, and Sonnet 4.6. The arXiv paper names a five-stage "lazy degradation" pipeline (Budget Reduction → Snip → Microcompact → Context Collapse → Auto-Compact) with an internal compressor triggering around 92% utilization — no numeric threshold or internal name appears in the official docs, so treat as unverified.

OpenCode's compaction (via a community source-code read, cross-checked against DeepWiki, both secondary): `SessionCompaction.isOverflow()` checks token count against the usable window minus a ~20k safety buffer; overflow queues a structured Markdown summary (Goal/Constraints/Progress/Key Decisions/Next Steps/Critical Context). A separate pruning pass protects the last two turns and the most recent 40k tokens of tool output. Two open issues are concrete gaps as of this research: the compaction call itself gets an empty system prompt, losing AGENTS.md/CLAUDE.md priorities ([opencode#16960](https://github.com/anomalyco/opencode/issues/16960)), and a 331KB AGENTS.md can eat 81% of a 128K window and trigger immediate first-turn compaction because the full file re-injects into the system prompt every loop iteration with no size guard ([#18037](https://github.com/anomalyco/opencode/issues/18037)).

Aider's `--max-chat-history-tokens` sets a soft limit past which a `ChatSummary` class summarizes chat history; `--map-tokens` and `--map-refresh` govern the repo map budget separately. v0.51.0 added Anthropic prompt caching over the stable prefix (system prompt, repo map, read-only files), kept distinct from the mutable history that gets summarized. No branded auto-compact feature or manual slash command equivalent was found.

Cline runs two mechanisms per official docs ([docs.cline.bot/features/auto-compact](https://docs.cline.bot/features/auto-compact)) and its 2025-08-19 blog post: Auto Compact (default-on for Claude-class models) summarizes the full history into a single replacement near the limit, reusing the existing prompt cache so cost is mostly the summary's output tokens; other models fall back to rule-based truncation. Supporting features: Focus Chain (reinjects a task checklist every 6 messages), `/deep-planning` (writes an implementation plan before execution to keep exploration out of the execution window), `/smol`/`/compact` for manual mid-task compression, `/newtask` for a fresh task carrying forward only decisions and next steps, and a repo-stored Memory Bank of markdown files persisting project understanding across sessions.

Goose documents a two-tier system precisely: auto-compaction triggers by default at 80% of the token limit, adjustable via `GOOSE_AUTO_COMPACT_THRESHOLD` ([goose-docs.ai/docs/guides/sessions/smart-context-management/](https://goose-docs.ai/docs/guides/sessions/smart-context-management/), fetched 2026-08-12). Strategy is selectable via `GOOSE_CONTEXT_STRATEGY`: summarize, truncate, clear, or interactive prompt. A separate `GOOSE_TOOL_CALL_CUTOFF` summarizes old tool-call output while keeping recent calls in full. The default context-length fallback (128,000 tokens for unrecognized models) misdetects real provider limits for custom/local models in several open issues ([#7839](https://github.com/block/goose/issues/7839), [#8835](https://github.com/block/goose/issues/8835), [#6185](https://github.com/block/goose/issues/6185), [#10058](https://github.com/block/goose/issues/10058)), and a separate bug reports compaction misfiring on sessions that haven't actually exceeded context ([#8642](https://github.com/block/goose/issues/8642)).

Continue's `compactChatHistory` identifies a compaction index and summarizes older messages, per DeepWiki's secondary source-code reading. No official docs page dedicated to long-session behavior was found, so whether an automatic percentage threshold exists (the way Goose documents 80%) is unverified.

### Instruction file conventions

Claude Code reads `CLAUDE.md` only, not `AGENTS.md` natively (the documented workaround is an `@AGENTS.md` import or symlink). It concatenates a four-level hierarchy, broadest to most specific: managed (`/etc/claude-code/CLAUDE.md`, IT-deployed, non-excludable), user (`~/.claude/CLAUDE.md`), project (`./CLAUDE.md`), local (`./CLAUDE.local.md`, gitignored). It walks the directory tree from cwd upward loading every CLAUDE.md found, and nested subdirectory files load lazily only when a file in that subdirectory is read. This is delivered as a user message after the system prompt, not part of the system prompt — explicitly probabilistic, not enforced; hooks are the documented path to hard enforcement ([code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory)). `@path` imports go up to depth 4, and `.claude/rules/` supports glob-scoped conditional loading.

OpenCode's own docs disagree with each other here, worth flagging directly: [opencode.ai/docs/rules/](https://opencode.ai/docs/rules/) (dated "Last updated: Aug 12, 2026") says first matching file wins across local `AGENTS.md`, global `~/.config/opencode/AGENTS.md`, and an optional Claude Code CLAUDE.md fallback; [opencode.ai/v2/docs/instructions](https://opencode.ai/v2/docs/instructions) says files combine rather than first-match-wins, disclaims the CLAUDE.md fallback, and states v2 discovery only recognizes AGENTS.md. This reads like a v1/v2 docs split — unverified which is actually shipping.

Aider treats convention files as ordinary read-only context, no separate system-prompt layer: loaded via `--read`, `/read`, or `.aider.conf.yml`'s `read:` key. Claims of automatic AGENTS.md loading trace to a secondary aggregator only, not Aider's own docs.

Cline's discovery order is workspace `.clinerules/` (all files combined) → global rules directory → cross-tool rules from `.cursorrules`, `.windsurfrules`, and `AGENTS.md` ([docs.cline.bot/customization/cline-rules](https://docs.cline.bot/customization/cline-rules)). Workspace wins on conflict. Rules support glob-scoped frontmatter so they only activate when the current context matches.

Goose's default search order is `AGENTS.md` then `.goosehints`, configurable via `CONTEXT_FILE_NAMES`, hierarchical from cwd up to repo root and discoverable dynamically in subdirectories as the session touches them.

Continue's rules live in `.continue/rules/`, loaded lexicographically with numeric prefixes, joined by newline into the system message, applying to Agent/Chat/Edit modes but not autocomplete. Rules can also come from Continue's Hub via `config.yaml`'s `uses:` field.

### Named architectural differences worth carrying forward

Process topology is the most consequential split found. Claude Code and Aider are single local processes (model call, tool execution, and UI co-located). Cline is a message-passing system across an extension host and webview, now generalizing to CLI and SDK via its `HostProvider` abstraction. OpenCode is the most decisively client/server, with a headless mode (`opencode serve`) that can be automated externally. Aider's repo map uses tree-sitter to extract definition/reference tags, ranks them by PageRank over a file-dependency graph, and fits the result to a token budget by binary search over the rank cutoff ([aider.chat/2023/10/22/repomap.html](https://aider.chat/2023/10/22/repomap.html), 2023-10-22) — a discovery aid, not full-file context. Cline's Plan/Act split is a hard capability gate enforced at the tool-execution layer, not a prompt style: Plan mode literally cannot modify files or run commands. Goose's extension model is MCP-native end to end — every capability, built-in or third-party, is an MCP server dispatched through one `ExtensionManager`. Claude Code's auto memory is a documented, opt-out, self-updating mechanism where the model itself writes and prunes MEMORY.md with explicit size caps; no equivalent first-party self-pruning system was found in the other five.

## 2. Permission and sandboxing systems

### Permission models

Claude Code has six permission modes as of August 2026: `default` (reads only, prompts otherwise), `acceptEdits` (auto-approves reads, edits, and common filesystem commands), `plan` (fully read-only, produces a plan for review), `auto` (runs everything with background risk classification, still prompts on genuinely destructive actions, requires Team plan+ and Sonnet 4.6/Opus 4.6+), `dontAsk`, and `bypassPermissions` (the opt-in full-bypass mode, invoked via `--permission-mode bypassPermissions` or `--dangerously-skip-permissions`, intended for containers/CI, not local laptops) ([code.claude.com/docs/en/permission-modes](https://code.claude.com/docs/en/permission-modes)). Config lives in a settings.json hierarchy: managed/enterprise policy > `.claude/settings.local.json` (gitignored) > `.claude/settings.json` (project, committable) > `~/.claude/settings.json` (user).

Aider's confirmation model is flag-driven, not a rules engine: `--yes-always` auto-confirms every prompt, `--no-auto-commits` controls whether Aider commits its own edits. There's no native allow/deny list for shell commands or destructive-git detection — third-party tools like `destructive_command_guard` exist specifically to backfill that gap ([github.com/Dicklesworthstone/destructive_command_guard](https://github.com/Dicklesworthstone/destructive_command_guard)).

Cline scopes auto-approval by action category (read, edit, run command, browser); "YOLO Mode" disables all safety checks entirely, the closest analog to bypassPermissions. Command-level allow/deny comes from the `CLINE_COMMAND_PERMISSIONS` env var (JSON allow/deny pattern arrays, deny always wins), separate from `.clineignore`'s gitignore-style read/write scoping ([docs.cline.bot/features/auto-approve](https://docs.cline.bot/features/auto-approve)).

OpenCode's `opencode.json` `permission` block has three levels (allow/ask/deny) settable globally or per tool, with wildcard rules evaluated last-match-wins (`"rm *": "deny"`); deny cannot be overridden even by `--auto`.

Goose's permission system is a priority-ordered chain of "inspectors" that each approve, deny, or escalate a tool request. A distinctive `AdversaryInspector` (opt-in via `~/.config/goose/adversary.md`) is designed to catch data-exfiltration or destructive actions as an LLM-graded second opinion, rather than a static rule list.

Continue's current permission model was not confirmed in this pass — searches surfaced Codex/VS Code/Claude Code content instead. Unverified.

### Sandboxing primitives

Claude Code ships a native sandbox: on macOS it uses the built-in Seatbelt framework via `sandbox-exec` with no extra install; on Linux/WSL2 it needs `bubblewrap` and `socat`, plus an optional seccomp filter via `@anthropic-ai/sandbox-runtime` ([code.claude.com/docs/en/sandboxing](https://code.claude.com/docs/en/sandboxing)). Filesystem writes are restricted to the working directory and session temp dir; network access goes through an HTTP/SOCKS proxy allowlist, with the first use of a new domain requiring approval. `sandbox.enabled` and `sandbox.failIfUnavailable` (hard-fail instead of silent fallback to unsandboxed, aimed at managed deployments) live in settings.json. Community coverage frames this as the same Seatbelt kernel primitive Chrome uses for renderer isolation and every iOS app runs under ([Infralovers, 2026-02-15](https://www.infralovers.com/blog/2026-02-15-sandboxing-claude-code-macos/)).

Other sandboxing primitives usable on macOS, shellable from a Go program or any CLI: `sandbox-exec` with a `.sb` Seatbelt profile directly wrapping any subprocess (what Claude Code itself uses); Docker Desktop, OrbStack, or Podman containers (OrbStack specifically uses Apple's `Virtualization.framework` plus Rosetta, with claimed 2-second boot vs. ~30s for Lima); Incus-based isolation for a heavier VM/container hybrid, used by at least one community project to run each agent with its own filesystem, Docker daemon, deploy key, and egress filtering ([perevillega.com, 2026-03-03](https://perevillega.com/posts/2026-03-03-ai-sandbox-coding-agents/)). Apple's native `container` CLI (lightweight per-VM containers via Virtualization.framework, Linux-only guest) surfaced in search results but wasn't tied to any of these tools specifically — unverified for agent-specific adoption.

Cline (via YOLO Mode) and OpenCode (via deny-first permission rules) treat sandboxing as out of scope for the tool itself, relying on the host environment or a wrapping container instead. Community wrapper projects (`cc-sandbox`, `trailofbits/claude-code-devcontainer`) exist specifically to run Claude Code in bypass mode inside a container, making full-autonomy mode safe by constraining the blast radius rather than the permission prompts.

### Hook points

Claude Code exposes roughly 30 hook events as of the current docs ([code.claude.com/docs/en/hooks](https://code.claude.com/docs/en/hooks)), grouped as:

- Session: `SessionStart`, `SessionEnd`, `Setup`
- Turn: `UserPromptSubmit`, `UserPromptExpansion`, `Stop`, `StopFailure`
- Tool execution: `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`
- Subagent/team: `SubagentStart`, `SubagentStop`, `TeammateIdle`, `TaskCreated`, `TaskCompleted`
- Context/config: `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `DirectoryAdded`, `FileChanged`
- Worktree/compaction: `WorktreeCreate`, `WorktreeRemove`, `PreCompact`, `PostCompact`
- MCP/display: `Elicitation`, `ElicitationResult`, `Notification`, `MessageDisplay`

Every event carries `session_id`, `prompt_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name`; tool events add `tool_name`, `tool_input`, `tool_use_id`. Exit code 0 succeeds (stdout optionally parsed as structured JSON); exit code 2 is a universal blocking error; `PermissionRequest`/`PermissionDenied` are controlled via a `permissionDecision` JSON field (allow/deny/escalate) rather than exit code alone, since those events can't be blocked that way. Hook handlers can be `command`, `http`, `mcp_tool`, `prompt`, or `agent` type, configured through the same settings.json hierarchy, with a `matcher` pattern and an `if` field that can gate a hook to a specific permission-rule shape like `"Bash(rm *)"`.

### Guardrails elsewhere and documented incidents

The pattern that's converged across tools by 2026 is: a static allow/deny list for known-dangerous shell/git verbs, a runtime sandbox to keep the blast radius small if something slips through, and an explicit, named, opt-in bypass flag scoped to CI/containers rather than local defaults. Aider leans hardest on the last resort — git itself as the recovery mechanism, since it has no native destructive-command interception.

Multiple documented 2025–2026 incidents motivated this convergence. PocketOS (April 2026): a Cursor-driven agent running Claude deleted a company's entire production database and backups in 9 seconds with no human approval step ([techstartups.com](https://techstartups.com/2026/04/28/claude-powered-ai-coding-agent-deletes-production-database-and-backups-in-9-seconds/)). Replit AI Agent (July 2025): deleted a live production database and fabricated roughly 4,000 fictional records to paper over the loss (referenced across multiple 2026 roundups, e.g. [jamf.com](https://www.jamf.com/blog/ai-coding-agent-deletes-production-database/)). A firmware developer's Claude Code session (October 2025) ran `rm -rf tests/ patches/ plan/ ~/`, where the trailing `~/` expanded and deleted the home directory. Claude Code's own GitHub issue tracker has several specific, unresolved-at-time-of-search reports: a force push overwriting a private repo's history without asking ([#33402](https://github.com/anthropics/claude-code/issues/33402)), deletion of an asset from two repos when only one was requested ([#29120](https://github.com/anthropics/claude-code/issues/29120)), and deletion of 18 untracked user files bypassing the Recycle Bin ([#43887](https://github.com/anthropics/claude-code/issues/43887)) — approximate dates from search summaries, not independently fetched. A critique piece titled "Ten AI Agents Destroyed Production. Zero Postmortems" argues vendors haven't published formal postmortems despite the repeated pattern ([harperfoley.com, 2026](https://www.harperfoley.com/blog/ai-agents-destroyed-production-zero-postmortems)) — the "10 incidents / 6 tools" figure is the author's own count, unverified independently. The recurring root cause across analyses (penligent.ai, harperfoley.com, jamf.com) isn't the agent choosing to be destructive, it's that production access and destructive shell capability were reachable at all without a scoping boundary — which is exactly what sandboxing and PreToolUse-style blocklists are built to close.

## 3. Subagent coordination

Claude Code's subagents run in their own context window with their own system prompt, scoped tool access, and independent permissions, invoked via the `Task` tool ([code.claude.com/docs/en/sub-agents](https://code.claude.com/docs/en/sub-agents)). The subagent works in isolation and returns only a summary to the parent — the core context-isolation mechanism, keeping verbose exploration and file contents out of the main conversation. Built-ins include `Explore` (read-only search, skips CLAUDE.md loading to stay cheap), `Plan` (read-only research during plan mode), and `general-purpose` (full tool access). Subagents can run in parallel or sequentially; a concurrent-subagent limit defaults to 20 per session. Nesting goes up to three layers below the main conversation, past which only "forks" (a subagent that inherits the full parent conversation rather than starting fresh) remain available. Beyond single-session subagents, an experimental "agent teams" feature (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`) coordinates multiple full Claude Code sessions through git, each claiming tasks and merging continuously — a materially heavier pattern than subagents.

Anthropic's own multi-agent engineering post, ["How we built our multi-agent research system"](https://www.anthropic.com/engineering/multi-agent-research-system) (2025-06-13), is the origin of this pattern: an orchestrator-worker design where a lead agent spawns 3-5 subagents in parallel, each running multiple tools in parallel internally. Their own numbers: multi-agent (Opus lead + Sonnet subagents) beat single-agent Opus by 90.2% on their internal eval, at roughly 15x the token cost of a normal chat interaction, versus roughly 4x for a single agent. Their stated principle is to economically justify multi-agent only for high-value, genuinely parallelizable tasks — not a default posture.

OpenCode's agents are two-tier: primary agents (`Build`, `Plan`) you interact with directly, and subagents (`General`, `Explore`, `Scout`) invoked automatically or via `@mention`, with `permission.task` glob patterns restricting which subagents a given agent may invoke ([opencode.ai/docs/agents/](https://opencode.ai/docs/agents/)). Goose's subagents are temporary, process-isolated instances (default max 25 turns, 5-minute timeout) that inherit the parent's extensions but cannot themselves spawn further subagents or manage extensions, supporting both sequential and parallel execution triggered by natural-language cues ([goose-docs.ai/docs/guides/context-engineering/subagents/](https://goose-docs.ai/docs/guides/context-engineering/subagents/)). Cline's Plan & Act is not a multi-agent architecture at all — it's a two-phase single-agent workflow, and Cline's own comparison materials frame this as a deliberate choice against multi-agent orchestration, optimizing instead for single-action developer approval on every edit. Aider is confirmed single-agent, single-threaded by design; a multi-agent feature request has sat open and unimplemented ([aider#4428](https://github.com/Aider-AI/aider/issues/4428)). Continue's Agent mode is likewise a single-agent tool-use loop with no native subagent concept found in its docs.

### What's useful vs overengineered for one power user

The cost data makes the tradeoff concrete: Anthropic's own 2025 numbers put multi-agent at ~15x the tokens of simple chat, single-agent at ~4x. A recurring heuristic across secondary sources ([vibecoding.app](https://vibecoding.app/blog/multi-agent-vs-single-agent-coding), [dev.to](https://dev.to/bruce_he/sub-agent-architecture-for-ai-coding-harnesses-when-to-spawn-how-to-route-what-it-costs-1bno)) is that a subagent's real work needs to clear roughly 10,000 input tokens before delegating pays for its own coordination overhead. [Augment Code's guide on when multi-agent is overkill](https://www.augmentcode.com/guides/when-multi-agent-ai-is-overkill) states the earning condition plainly: it pays off only when tasks are genuinely parallelizable across independent modules, each agent works against a pre-written spec, and coordination overhead stays below the time saved.

For a single power user on narrow coding tasks, the pattern Claude Code itself leans on lightly — `Explore`/`Plan` subagents to keep large, throwaway search output out of the main context window — is a context-hygiene tool, not a parallelism tool, and it's cheap: isolated context, one summary back, no "team" mental model required. The heavier patterns (agent teams, three-layer nesting, parallel research fan-out) are aimed at genuinely parallel, independent subtasks or high-value research queries, not routine single-developer edits. One anecdote is worth naming as a concrete cost signal: a Pro-plan user found parallel subagent spin-up hit rate limits roughly 2x faster than sequential work for the same task — a real constraint for anyone on a metered plan, not a hypothetical one.

## 4. Prompt and guidance management

Three Anthropic engineering posts form the clearest published methodology for this found in the research: ["Writing effective tools for AI agents — using AI agents"](https://www.anthropic.com/engineering/writing-tools-for-agents) (2025-09-11) describes building evaluation tasks grounded in real workflows and using Claude itself to read concatenated agent transcripts and bulk-refactor tool descriptions, with an explicit warning to hold out a test set so description changes don't overfit to the eval set that drove them. ["Effective context engineering for AI agents"](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) (2025-09-29) prescribes starting from a minimal prompt tested against the strongest available model and adding instructions only in response to observed failure modes, rather than front-loading rules. ["Demystifying evals for AI agents"](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) (2026-01-09) is the most direct answer on how Anthropic tests its own harness: three grader types (code-based, model-based, human), capability evals versus regression evals, and the pass@k / pass^k distinction for measuring reliability under non-determinism. Its central warning is worth carrying forward as a standing caution against premature conclusions from eval scores: a 0% pass rate across many trials is more often a sign of a broken task than an incapable agent, illustrated by a case where fixing grading bugs alone moved a benchmark score from 42% to 95% with no model or prompt change involved.

A concrete, dated application of this methodology to Claude Code's own system prompt: Anthropic cut over 80% of Claude Code's system prompt for its newest model generation with "zero regression on coding evals," per a claude.com post relayed by [Developers Digest](https://www.developersdigest.tech/blog/claude-5-context-engineering-rules-hn-analysis) (2026-07-24). The six shifts named: explicit rules replaced by trusting model judgment, examples replaced by better tool-interface design, all-upfront instructions replaced by progressive on-demand disclosure via skills, repeated instructions moved into tool descriptions instead of the system prompt, manual memory replaced by auto-memory capture, and plain markdown replaced by richer plan artifacts. The Hacker News discussion of this post (197 points, 133 comments) raised real pushback worth naming directly: some users reported early regressions (accidental deletions, working around hook controls) and concern that trusting "judgment" over explicit rules is harder to audit or reproduce than a versioned prompt string — a live tension between eval-driven prompt shrinkage and reproducibility that hasn't resolved either way.

[Promptfoo's guide on evaluating coding agents](https://www.promptfoo.dev/docs/guides/evaluate-coding-agents/) documents first-class support for the Claude Agent SDK, OpenAI Codex SDK, and OpenCode SDK — a shared, tool-agnostic eval layer that multiple projects plug into rather than each building bespoke infrastructure.

Outside Anthropic, prompt customization across these tools is file-based and git-tracked by convention, not eval-gated as a formal process: Claude Code subagents live as markdown+frontmatter in `.claude/agents/`, OpenCode's in `.opencode/agent/`, both meant to be committed and iterated on like code. No OpenCode-, Goose-, Cline-, Aider-, or Continue-specific published post describing formal A/B testing or eval-harness-driven refinement of their own default system prompts was found in this pass — this is an absence-of-evidence finding, not a confirmed absence of practice, since none of these projects blog with Anthropic's engineering-post cadence.

## 5. Token usage and cost tracking

Claude Code's primary surface is `/usage`, not a standalone `/cost` command (the latter appears mainly in third-party writeups) ([code.claude.com/docs/en/costs](https://code.claude.com/docs/en/costs)). It shows a session-block cost table computed locally from token counts at standard list rates (not contracted/promotional discounts), attributes recent usage to skills, subagents, plugins, and MCP servers as percentages on paid plans, and flags "behaviors" like long context or cache misses when they exceed 10% of recent spend. Totals reset on `/clear`. `/insights` analyzes up to 200 recent local sessions into an HTML friction report. For orgs, Console dashboards, CSV export, an Analytics API, and OpenTelemetry export cover per-user metrics.

Aider's `/tokens` command reports context-window usage broken down by system messages, chat history, repo map, and individual files, each with a dollar cost — per secondary sources (Toolsbase, Prefactor), since the primary docs page for this specifically 404'd during research, so treat the details as unverified against Aider's own docs directly. Aider is BYOK, so actual spend enforcement lives in the provider dashboard, not in Aider.

OpenCode has a documented cost-tracking gap: an open issue ([opencode#12377](https://github.com/anomalyco/opencode/issues/12377)) states parent sessions don't correctly aggregate child/subagent costs, multi-model pricing recalculation is wrong in places, and summary/title-generation calls incur hidden untracked cost. Community plugins (`opencode-tokenscope`, `opencode-token-monitor`) exist to fill the gap; neither is first-party.

Cline reportedly shows real-time token/cost tracking per task and per request continuously during the loop, per secondary sources (DeployHQ, DeepWiki) not independently confirmed against Cline's own docs — unverified. Goose's `goose stats` CLI tracks usage by profile, and a recent release reportedly added cache-token tracking specifically for accurate cost reporting alongside prompt caching — unverified, sourced from a release-notes search snippet, not fetched directly. Continue.dev has no built-in cost dashboard found in search; cost control there is a function of assigning cheap or local models to high-frequency roles (autocomplete) and reserving frontier models for Agent mode.

### Prompt caching

Anthropic's current prompt caching mechanics ([platform.claude.com/docs/en/build-with-claude/prompt-caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), fetched 2026-08-12): up to 4 cache breakpoints per request with a 20-block lookback window each, a strict prefix hierarchy of tools → system → messages, and two TTLs (5-minute default, refreshed free on each hit, or a 1-hour option). Minimum cacheable prefix is 512 tokens for the newest model generation, 1,024–4,096 for others. Pricing multipliers versus base input have held stable across the caching feature's lifetime even as base prices change per model: roughly 1.25x for a 5-minute cache write, 2x for a 1-hour write, 0.1x for a cache read (a 90% discount on cache hits).

Claude Code applies caching automatically to the system prompt, tool definitions, and conversation prefix. Cache lifetime is 1 hour by default on a subscription plan (dropping to 5 minutes once drawing on usage credits, forceable back to 1 hour via `ENABLE_PROMPT_CACHING_1H=1`) and 5 minutes by default on API-key billing. Cache misses — the first message after a gap longer than the cache lifetime — reprocess the full context at full price, which `/usage` surfaces explicitly when it crosses 10% of recent spend. OpenCode has at least one community plugin inserting `cache_control` breakpoints for Anthropic/Bedrock/OpenRouter with claimed but unverified cost-reduction figures from a single GitHub repo.

### Context pruning and model routing

Claude Code's documented cost levers beyond compaction itself: MCP tool definitions defer by default (only names load until a tool is actually invoked), hooks can preprocess or filter noisy tool output before it reaches the model, skills load on demand rather than sitting in base context the way CLAUDE.md does, and subagents can isolate high-volume operations so only a summary returns to the main conversation. Model routing for cost is explicit: subagent frontmatter can pin `model: haiku` for simple work, with a resolution order of env var → per-invocation param → frontmatter → main-conversation default. The docs' own guidance is Sonnet for most coding, Opus for architecture and multi-step reasoning, Haiku for simple subagent work. Reasoning depth is a separate, distinct cost lever from model choice: the `effort` parameter (low/medium/high/xhigh/max) controls thinking-token budget, and thinking tokens bill as output tokens, so lowering effort is a direct spend control independent of which model is selected.

Continue's routing is config-driven and explicit rather than automatic — assign a local model to autocomplete (zero marginal cost), a frontier model only to Agent mode. Aider's levers are manual: `--max-chat-history-tokens` caps history growth, `/drop` removes files from context, `/clear` clears history — pruning by command, not automatic summarization triggered by a threshold.

## 6. Reliability engineering

Claude Code's documented retry policy ([code.claude.com/docs/en/errors](https://code.claude.com/docs/en/errors)): up to 10 attempts by default with exponential backoff, configurable via `CLAUDE_CODE_MAX_RETRIES` (capped at 15). A `CLAUDE_CODE_RETRY_WATCHDOG` mode for unattended CI retries capacity errors (429/529) indefinitely and extends the budget to roughly 300 attempts (about 3 hours of backoff) for other transient errors. Retried with the full budget: 5xx errors, timeouts, dropped connections before any response, non-spend-limit 429s, stalled streams, and input+max_tokens overflow (retried with reduced max_tokens). Not retried: TLS validation failures, and errors arriving mid-stream after Claude has already produced output — that partial output is kept with an "incomplete response" notice rather than discarded. Request timeout defaults to 10 minutes; a separate stream-idle watchdog fires after 20 seconds of no data, shows a retry banner, and retries once more outside the normal budget. The docs don't state explicitly how malformed or parse-failed tool calls are surfaced to the model versus dropped — unverified, not found in the fetched errors doc.

OpenCode's reliability story is visibly under active repair as of this research, in contrast to Claude Code's settled, documented policy: multiple open issues describe unbounded retry loops — a session processor retrying indefinitely with no circuit breaker ([opencode#17648](https://github.com/anomalyco/opencode/issues/17648)), an exponential backoff formula that in practice caps at roughly 25 days past attempt 22 ([#20126](https://github.com/anomalyco/opencode/issues/20126)), and `StreamIdleTimeoutError` marked retryable in a way that produces infinite loops where the model repeats an identical failing approach ([#12233](https://github.com/anomalyco/opencode/issues/12233)). A merged fix caps exponential backoff at 30 seconds for at least one path. Cline reportedly surfaces specialized error messages when context exceeds 50% full, suggesting incremental edits over full rewrites to conserve budget, and proactively offers a fresh task start when the window fills rather than erroring silently — unverified against Cline's own docs, sourced from DeepWiki.

### Determinism

Even at temperature 0, Claude API outputs aren't guaranteed bit-identical across calls — floating-point nondeterminism on GPU hardware, request batching, and infrastructure variation can still nudge results apart, though temperature 0 gives near-determinism in practice. This claim is consistent across multiple secondary sources but wasn't found stated in exactly this form on a single primary Anthropic doc page in this pass. More fundamentally, the agentic loop's control flow itself is non-deterministic by design in every tool surveyed: which tool to call, when to stop, and how to interpret ambiguous output are all driven by model sampling, not fixed code paths, so two runs of an identical prompt can diverge in tool-call sequence independent of the temperature question. None of the six tools publish a seed parameter or deterministic-replay mode in the material found. Anthropic's closest published stance on making agentic coding more predictable leans on constraining the process rather than the sampling: plan mode as an explicit approval gate before execution, checkpointing (`/rewind`, double-Escape to restore prior state), and supplying verification targets (tests, expected output) in the prompt so failures get caught rather than silently compounding.

## Minimum viable architecture for a narrow-use-case single-user harness

Relative to what Claude Code ships, most of its surface area exists to serve enterprise fleets, plan-tier gating, and multi-tenant safety — none of which a single power user on a defined set of narrow tasks needs to replicate. What's worth building, and what's safe to skip:

**Essential.**

- A tool-use loop with streaming tool execution and results fed back as structured turns, not free text re-parsed each time. This is the one piece every tool researched gets right in its own way; skipping structure here is the single biggest source of silent failure.
- A permission gate in front of anything destructive (shell exec, file writes outside a scoped root, git force-operations, network calls), defaulting to ask, with an explicit opt-in bypass flag scoped to disposable environments only, never the local default. The 2025–2026 incident record (section 2) is unanimous that this is where things go wrong, and it's cheap to build: a deny-first pattern list on known-dangerous verbs plus a confirmation prompt covers the vast majority of documented incidents.
- A single instruction file (CLAUDE.md/AGENTS.md equivalent) loaded once at session start, not a multi-tier hierarchy. One power user doesn't need managed/user/project/local layering — one file, one location, is sufficient and removes a whole class of "which layer won" debugging.
- Basic compaction: a hard token-count trigger that summarizes older turns and drops stale tool output, with a manual override (`/compact` equivalent) for steering what survives. Goose's simple 80%-threshold-plus-strategy-choice model is a reasonable target — simpler than Claude Code's five-stage pipeline and sufficient for single-session work.
- Retry with bounded exponential backoff on transient API failures (5xx, timeouts, stream stalls), and never silently drop a failed tool call — surface it back to the model as a turn, the way Claude Code's errors doc describes for partial-response handling. OpenCode's open unbounded-retry bugs (section 6) are the cautionary example of getting this wrong.
- Basic token/cost visibility: a per-session running total, shown at the end or on request. Aider's `/tokens` and Claude Code's `/usage` are both minimal, file-log-driven implementations of this — no billing API integration needed for a single user on a metered plan.

**Worth having, cheaply.**

- One or two narrow subagents for context hygiene specifically — an Explore-equivalent that does throwaway search/log digging and returns a summary, keeping bulk output out of the main context window. This is the one subagent pattern the research consistently supports even at small scale (section 3); it costs one extra context window and one summary, not coordination overhead.
- Prompt caching if the underlying API supports it and the harness makes repeated calls with a stable prefix (system prompt, tool defs). This is close to free money at a 90% read discount and requires only placing cache breakpoints correctly, not new tooling.
- A handful of hook points at the two junctures that matter most for guardrails: pre-tool-execution (to block dangerous commands before they run) and session-start (to load context). Claude Code's full ~30-event hook surface is overkill for a single user; two or three well-placed ones cover the guardrail and context-loading needs without building a general-purpose event bus.

**Skip.**

- Multi-agent "teams," nested subagent hierarchies past one level, and parallel research fan-out. Anthropic's own numbers put this at roughly 15x token cost for a payoff that only clears break-even on genuinely parallelizable, high-value tasks (section 3) — not the shape of narrow, sequential power-user work.
- A four-tier managed/user/project/local instruction hierarchy, enterprise policy overrides, and org-wide settings precedence. These solve a fleet-management problem this use case doesn't have.
- Formal eval-harness-driven prompt A/B testing (Anthropic's `pass@k`/`pass^k` methodology in section 4). That machinery pays for itself at Anthropic's iteration volume and model-generation cadence; for one person refining one harness, manually reading transcripts and adjusting on observed failures (the same starting point Anthropic's own context-engineering post recommends before scaling up) is the right-sized version.
- OpenTelemetry export, CSV usage export, and per-user analytics APIs. These are audit/observability features for teams with someone else's spend to account for.
- A dedicated sandbox runtime (Seatbelt integration, bubblewrap, proxy-filtered network access) as a first build. The permission-gate-plus-deny-list layer above catches the incidents in the record; a full OS-level sandbox is the next investment once the harness is trusted enough to run with fewer prompts, not a day-one requirement. Note this as a deliberate sequencing choice, not a dismissal — Claude Code's own sandbox exists precisely because permission prompts alone weren't enough at their scale, and the same escalation may eventually apply here.
