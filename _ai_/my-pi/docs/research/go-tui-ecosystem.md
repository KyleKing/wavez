# Go terminal-UI ecosystem for a coding-agent CLI (August 2026)

Research conducted 2026-08-12 via WebSearch/WebFetch against primary sources (GitHub repos, tags/releases pages, pkg.go.dev, crates.io, npm, PyPI, security advisories, and the source of `charmbracelet/crush` itself). Dates are stamped throughout. Claims that couldn't be pinned to a primary source are marked `[unverified]`.

## TL;DR

Bubble Tea is the right default for a Go coding-agent CLI. The ecosystem is actively maintained (all five core Charm libraries cut v2 releases in Feb-Mar 2026 and kept patching through August 2026), Charm shows no sign of the funding/org trouble sometimes associated with 2024, and Charm's own AI coding agent, Crush (27.3k GitHub stars), is a working, production-scale reference implementation for almost every hard problem this project will hit: streaming tokens, syntax-highlighted diffs, virtualized scrollback, split layout, mouse handling, and async updates from goroutines. None of the Go alternatives (tview, gocui, termui) or the non-Go options (Ratatui, Textual, Ink) is a clear win over Bubble Tea for a team already writing Go. For remote/mobile access, don't reach for Wish first — Crush's own answer is `crush serve`, an HTTP/SSE client-server split, and that's the shape to copy.

## 1. Charm ecosystem maturity

### Bubble Tea

Latest stable is **v2.0.8** (July 3, 2026). v2.0.0 shipped February 24, 2026 — the framework's first breaking-change release ever, after years on v1 (last v1 release v1.3.10, September 17, 2025). Cadence since has been monthly-to-biweekly: v2.0.1 (Mar 2), v2.0.2 (Mar 9), v2.0.3-v2.0.5 (Apr 13), v2.0.6 (Apr 16), v2.0.7 (Jun 1), v2.0.8 (Jul 3). ([tags](https://github.com/charmbracelet/glamour/tags))

Known limitation for a coding agent: Glamour renders a complete, static document with a stylesheet-based approach rather than incremental diffing. Streaming partial markdown token-by-token into Glamour architecturally implies re-rendering the whole buffer on each update, not an incremental append — this is an inference from Glamour's whole-document design, not something Charm states explicitly, so flagged `[unverified]`. In practice, Crush doesn't route per-token LLM output through Glamour at all (see §2 below); it uses Glamour for complete rendered documents.

## 2. Bubble Tea's fit for coding-agent TUI needs

The single best evidence source here is **Crush's own source code** (`charmbracelet/crush`, cloned and inspected directly), Charm's own AI coding agent and the closest real analog to "Claude Code in Go." Its `go.mod` pins `bubbletea/v2 v2.0.8`, `bubbles/v2 v2.1.1`, `lipgloss/v2 v2.0.5`, plus `chroma/v2` for syntax highlighting and `go-udiff` for diffing.

**Streaming output.** The standard pattern is a self-re-arming `tea.Cmd`: read one item off a channel, return it as a message, and the handler for that message returns a new `Cmd` that reads the next item — no goroutine ever touches model state directly. For LLM tokens specifically, Crush doesn't drain a raw channel in `Update` at all: it publishes updates through a `pubsub.Broker[T]`, and a background goroutine calls `program.Send(ev.Payload)` for each event — `Program.Send` is Bubble Tea's sanctioned way to push messages from outside the event loop. A load-bearing performance detail: Crush's code explicitly does *not* trigger busy-state/workspace re-probes on every per-token update, only on turn-start — a comment notes doing so "would put workspace probes on every token." Flicker avoidance is now partly a protocol concern: v2's Mode 2026 synchronized output pushes a full frame atomically.

**Syntax-highlighted diffs.** Chroma (`alecthomas/chroma/v2`) is the de facto highlighter in the Charm ecosystem. Crush wires it directly into Lip Gloss with a custom formatter, and — critically — memoizes lexer-by-filename lookups behind a mutex-guarded map because a comment in the code states plainly that naive `lexers.Match()` calls "dominated resize cost in large, code-heavy sessions where every diff and code view re-matched on each frame." A dedicated `diffview` package (826 lines) builds on `go-udiff` (a Go difflib port) plus Chroma, with a second cache layer keyed by content-hash so unchanged lines aren't re-highlighted every frame. This two-layer caching (lexer-by-filename, highlighted-line-by-content-hash) is a directly reusable pattern, not a hypothetical — it exists because naive re-highlighting was a measured bottleneck in production.

**Scrollable panes.** The most surprising finding: **Crush does not use the stock `bubbles/v2` `viewport` component for chat history at all.** It hand-rolls a virtualized list (`internal/ui/list/list.go`) with lazy rendering, an `offsetIdx`/`offsetLine` scroll cursor, and a comment stating the explicit goal: "per-frame work is O(viewport) rather than O(total item heights)." This matches known stock-`viewport` complaints — [bubbletea#1017](https://github.com/charmbracelet/bubbletea/issues/1017) ("visible area may seem incorrect when content exceeds viewport width") and [#919](https://github.com/charmbracelet/bubbletea/issues/919) (scroll position lost when content is replaced) — the same class of bug Claude Code itself has hit ([anthropics/claude-code#60345](https://github.com/anthropics/claude-code/issues/60345), [#28077](https://github.com/anthropics/claude-code/issues/28077)). Practical read: stock `viewport` is fine for a bounded pane (help text, a fixed log tail) but not for an unbounded, mixed-height, sticky-bottom-during-streaming chat transcript — build a virtualized list instead, the way Crush did.

**Split panes / layout.** Bubble Tea has no first-class layout system — only `tea.WindowSizeMsg` (width/height in cells). Everything else is manual arithmetic, or a third-party layout package. [`winder/bubblelayout`](https://github.com/winder/bubblelayout) is a MiG-Layout-inspired option, but its own README admits it lacks padding/margin, visibility toggling, and priority-based space allocation. **Crush doesn't use it** — it hand-propagates resize through explicit `updateLayoutAndSize()` calls and covers the result with a dedicated `layout_test.go`. Documented community pain ([discussion #943](https://github.com/charmbracelet/bubbletea/discussions/943), [leg100's write-up](https://leg100.github.io/en/posts/building-bubbletea-programs/)): "you think of it like the web's box model, but don't have those tools"; components created after startup can render at zero size until the next resize event fires. Budget real engineering time for this — either accept `bubblelayout`'s gaps or write and test manual size-propagation code like Crush does.

**Mouse support.** v2 replaced v1's single generic `tea.MouseMsg` with granular types (`MouseClickMsg`, `MouseWheelMsg`, `MouseMotionMsg`) exposed via an `OnMouse` handler on `tea.View`. There is still no built-in hit-testing — the accepted third-party answer is [`lrstanley/bubblezone`](https://github.com/lrstanley/bubblezone), which marks rendered regions with zero-width sequences and resolves clicks against them. Crush doesn't use bubblezone either — it hand-writes coordinate math against tracked pane bounds (`handleClickFocus`, `ItemIndexAtPosition`). Either approach (bubblezone, or hand-rolled bounds tracking) is standard; nothing ships this for free.

**Terminal resizing.** `WindowSizeMsg` fires once at startup and on every resize (SIGWINCH on Unix; Windows has no SIGWINCH equivalent, a known platform gap, current v2 workaround `[unverified]`). It's delivered only to the root model — cascading it to children is entirely the application's job. Crush's list component does selective invalidation: it drops its cached total-height figure only on width changes, not height changes, since height changes don't affect wrapped line counts — a concrete resize-performance optimization worth copying.

**Async updates from goroutines.** The canonical rule, repeated in Charm's own docs and the community: never mutate model state from a goroutine. `tea.Cmd` runs in its own goroutine, and Bubble Tea feeds the resulting `Msg` back into a strictly serial `Update` loop — that serialization is the entire safety mechanism. For long-lived streams, `Program.Send(msg)` is the sanctioned escape hatch, used exactly as described above in Crush. Two real gotchas: message ordering across concurrently-running commands is not guaranteed (Crush's fix: make each stream chunk's handler responsible for reading the next chunk, serializing that one stream by construction), and an unrecovered panic inside a goroutine feeding `program.Send` can silently crash the whole program — Crush wraps its subscription goroutine in `defer log.RecoverPanic(...)` specifically to convert that into a graceful shutdown. Worth copying directly. Bubble Tea itself has had races in this exact area ([PR #1375](https://github.com/charmbracelet/bubbletea/pull/1375)), so treat it as a live area, not settled.

**Performance at scale.** All four Crush optimizations above (cached lexer lookups, content-hash-cached highlighted lines, virtualized scrollback, suppressed per-token side effects) exist because the naive approach measurably didn't scale for long agent sessions — this is documented in code comments, not speculation. Separately, an **open, unresolved regression** is worth flagging: [bubbletea#1724](https://github.com/charmbracelet/bubbletea/issues/1724) (opened 2026-06-25, still open) reports v2's cursedRenderer processing scroll frames 3-8x slower than v1 (300-800µs vs 50-100µs) in continuous-scroll scenarios like log viewers or chat interfaces — root cause is a full ANSI-parse-to-cell-diff pipeline running every line every frame even when most lines just shifted. A proposed fix claims 72-83% improvements but has no maintainer response yet as of this research.

## 3. Go alternatives to Bubble Tea

| Library | Latest activity (2026) | Architecture | Fit for coding-agent CLI |
|---|---|---|---|
| **tview** | Commit Aug 11, 2026; latest tag v0.42.0 (Aug 27, 2025), deliberately kept pre-1.0 | Retained-mode widget tree (`Flex`, `Grid`, `Pages`), callback-driven, no Model/Update/View loop | Best stock fit: built-in scrollable `TextView` with auto-scroll and region-tag coloring, `Flex`/`Grid` for split layout, mouse built in — but async correctness is manual (`QueueUpdateDraw`), no message-passing safety net |
| **gocui** | Active fork `awesome-gocui/gocui`, commit Feb 9, 2026 after a multi-year dormancy; a second fork backs lazygit, which has since vendored its own copy rather than depend on it externally | Minimalist window/view manager over tcell, no Elm loop | Low-level; streaming/scrolling/layout all hand-rolled. Workable if you want tight control, but you rebuild what tview already has |
| **termui** | Last commit July 10, 2025; explicit README notice asking for maintainers; no 2026 commits found | Dashboard/widget-render model (charts, gauges, sparklines) | Weakest fit — built for glanceable dashboards, not conversational transcripts; no rich text-input widget |
| **tcell** | Actively maintained (commit Aug 10, 2026, monthly cadence, only 8 open issues) | Not a UI framework — it's the terminal I/O layer tview and gocui sit on | Maximum control, maximum work: no widgets at all, you'd reimplement tview's widget layer from scratch |

None beats Bubble Tea outright for this use case. **tview is the one credible alternative worth naming** — it's the only option with a scrollable, color-taggable text view and flex/grid layout built in, which matches a coding-agent transcript's shape without hand-rolling those primitives. Its cost is architectural: no Elm-style Model/Update/View, so state management and async correctness fall on manual `QueueUpdateDraw` discipline instead of a message-passing pattern. For a project already invested in Bubble Tea's architecture, switching would trade a proven pattern for a richer stock widget set — not a clear win either direction. gocui and termui are both worse fits than tview specifically for this use case.

## 4. Non-Go alternatives (if open to switching languages)

| Framework | Language | Latest (2026) | Production AI-CLI proof | Remote/mobile story |
|---|---|---|---|---|
| **Ratatui** | Rust | 0.30.2 (Jun 19, 2026); still pre-1.0 four+ years after forking tui-rs | **Yes — OpenAI's Codex CLI runs on it today**, having rewritten from TypeScript/Ink to Rust+Ratatui in 2025-2026 specifically to drop the Node runtime | None first-party; would need to hand-wire an SSH-to-pty bridge |
| **Textual** | Python | 8.2.8 (Jun 30, 2026), "Production/Stable" | None found — no major AI-coding-CLI built on it surfaced in this research (evidence gap, not proof of absence) | Strongest of the three: `textual-web`/`textual-serve` are official, first-party, ready-to-use (browser-tab access via websocket) |
| **Ink** | Node/React | 7.1.1 (Jul 16, 2026) | **Historical only** — both Claude Code and Codex CLI started on Ink; Claude Code now runs a heavily forked, Ink-derived custom renderer, and Codex has since left Ink entirely for Ratatui | None first-party |

The most load-bearing finding here: **the two flagship AI coding CLIs that started on stock Ink have both since moved away from it** — Codex to Rust/Ratatui, Claude Code to a bespoke fork — and the documented reason is performance under exactly the workload a coding agent produces (high-frequency token-by-token re-renders; Ink "rebuilds the entire layout and output on every update," per its own docs). Ratatui has the strongest current production proof for this specific application category (Codex CLI, live, today). Textual has the best-documented streaming ergonomics and the only shipped SSH/web-remote story of the three, but no comparable flagship AI-CLI adoption evidence.

**Does switching languages change velocity or capability?** Within the TUI layer alone, it's close to a wash: each framework has comparable maturity, and no single one is a clear unlock over Bubble Tea/Lip Gloss for a team already fluent in Go. Textual's edge on streaming ergonomics and remote access is real but not transformative. The decision that actually matters is different: **picking a non-Go TUI layer means either moving the whole agent core to that language too, or accepting a subprocess/FFI boundary between a Go core and a non-Go UI** — and Codex's own migration argues against the latter. OpenAI moved *away* from a split TS-UI/Rust-core-style architecture specifically to get a single static binary with no runtime dependency and no GC pauses. That reasoning applies in reverse to a Go team: bolting a Rust, Python, or Node TUI onto a Go core reintroduces the same deployment complexity Go's static binary avoids by default. Rust is the one candidate where a full-core rewrite is plausible without giving up single-binary distribution (Rust and Go both compile to static binaries); Python and Node both cost that property outright unless paired with a packager that has its own maturity tradeoffs.

## 5. Real-world pain points and architecture patterns

**OpenCode is not a Bubble Tea reference — the premise doesn't hold.** `sst/opencode` (now showing under the `anomalyco` org) is a TypeScript/Bun monorepo. There's no `.go` file, no `go.mod`, and no reference to Bubble Tea anywhere in the repo. No evidence of an earlier Go/Bubble Tea era was found either. If you've heard OpenCode described as a Go/Bubble Tea tool, that's not borne out by the current codebase.

**Crush is the real Go/Bubble Tea reference, and it did not absorb OpenCode.** `charmbracelet/crush` (27,311 stars as of 2026-08-12) began as an independent project by Kujtim Hoxha; Charm's Christian Rocha traveled to meet Hoxha and the project joined the Charm org, with Hoxha staying on. Charm's own blog post describes this clearly, with no mention of OpenCode — a prompt premise this research disproved rather than confirmed.

**Crush's architecture explicitly rejects the textbook nested-`tea.Model` pattern**, and this is the single most load-bearing finding of this whole research pass. Its contributor doc (`internal/ui/AGENTS.md`) states directly:

- "The `UI` struct serves as the sole Bubble Tea model" — one flat model, not many nested ones. Sub-components don't implement `Update`; the parent calls targeted imperative methods on them directly.
- Explicit contributor guidance: "Separate logic into files rather than nesting models" and "Prefer direct state mutation over command-based message sending" — a direct rejection of the message-passing-heavy composition style Bubble Tea's own tutorials teach ([the pattern that originates from issue #175](https://github.com/charmbracelet/bubbletea/issues/175), 2021).
- All routing (dialog interception, focus-based dispatch, state-based dispatch) happens centrally in one big `Update` on the `UI` struct.
- Rendering is a hybrid pipeline: a screen-buffer approach (Charm's newer, dev-only Ultraviolet library) for most components, with some sub-components (the generic list) still rendering strings that get painted onto the buffer.
- Message/item types use interface layering (`list.Item` → `MessageItem` → `ToolMessageItem`) with opt-in capability interfaces (`Focusable`, `Highlightable`, `Expandable`, `Animatable`), not one god-type.
- Dialogs get their own small interface (`ID()`, `HandleMsg()`, `Draw()`) managed as a stack, and one specific named fix — `OpenDialogWithGrace` — absorbs in-flight keystrokes for 425ms-1.5s after opening a dialog specifically to stop keystrokes meant for the previous focus target from acting on the newly opened one. This is a concrete, named solution to the keyboard-routing-conflict problem across nested/overlapping components.
- Explicit performance rules are baked into the contributor doc: expensive operations go through `tea.Cmd`, never in `Update`; the list uses lazy rendering; chroma styles/lexer lookups must be memoized.

Other Go AI-CLI-on-Bubble-Tea projects exist but are all small (largest at 306 stars) with no comparable architecture documentation — none is a credible second reference point.

**Bubble Tea's own community has open, unresolved complaints about complexity at scale**, both from April 2026 and still open as of this research: a proposal for a devtools inspector ([#1655](https://github.com/charmbracelet/bubbletea/issues/1655), "no way to inspect message flow, current model state, or component hierarchy at runtime") and a proposal for a testing framework ([#1654](https://github.com/charmbracelet/bubbletea/issues/1654), "there is no standard way to test Bubble Tea applications," citing brittle manual `Update()`-poking tests and teams skipping TUI testing entirely due to friction). Charm's own `teatest` package (documented in [a 2026 blog post](https://charm.land/blog/teatest/)) partially addresses this but is still marked experimental (`x/exp/...` import path) years after publication — itself evidence it didn't fully solve the problem. A real nested-state bug report ([#1522](https://github.com/charmbracelet/bubbletea/issues/1522)) describes a 12+ case state-switch failing to propagate a child model's exit command correctly — exactly the class of bug the devtools/testing proposals exist to catch earlier. Crush's own golden-file test suite for its diff view (per-mode, per-width, per-theme snapshots) is a concrete example of teams filling that testing gap themselves rather than waiting on the framework.

**Architecture takeaway for a from-scratch build:** don't default to deep nested `tea.Model` composition once the app gets complex. Crush's pattern — one flat top-level model, imperative calls to non-`tea.Model` sub-components, centralized routing, and a capability-interface approach for polymorphic list items — is the proven shape for a nontrivial coding-agent TUI in Bubble Tea, and it exists precisely because the textbook nested-model pattern doesn't hold up at this scale.

## 6. SSH/remote terminal serving

**Wish** ([charmbracelet/wish](https://github.com/charmbracelet/wish), latest v2.0.3, July 31, 2026) wraps `gliderlabs/ssh`, which wraps the standard library's `x/crypto/ssh`. Each incoming SSH connection gets its own `tea.Program` with the pty wired directly to it. Auth (public key, password, keyboard-interactive, or none) is handled at the `gliderlabs/ssh` layer — "accept all connections" is the default unless the app supplies a handler.

**Two security advisories landed in 2026, one critical:**

- **CVE-2026-41589** (CVSS 9.6, critical) — an SCP path-traversal bug in Wish's SCP middleware. `filepath.Clean()` resolved `../` sequences without rejecting them, letting an SSH user read/write arbitrary files outside the configured root — a path to RCE via mechanisms like cron or SSH key injection. Affected v2.0.0, patched in v2.0.1. Published (per the GitHub Security Advisory) around April 17, 2026 — earlier research this session cited May 7, exact day flagged `[unverified]`, but the fix version (2.0.1) and CVSS score are confirmed against the GHSA. ([GHSA-xjvp-7243-rg9h](https://github.com/advisories/GHSA-xjvp-7243-rg9h))
- **GHSA-h9g8-jhcw-5hgp** (CVSS 7.5) — Wish pinned an outdated `x/crypto/ssh` carrying three pre-auth DoS CVEs (a decoder panic, a goroutine-leak, and key-parser resource exhaustion). Any unauthenticated client that can open a TCP connection could crash the process or exhaust memory. Published August 1, 2026, patched in v2.0.2+.

**Run v2.0.3 or later, full stop, and require public-key auth explicitly** — don't rely on the default accept-all policy. Two critical-severity bug classes landing in one library within a few months of each other is a real signal about the blast radius of running an internet-facing SSH server, not an isolated incident.

**No first-party Charm product exists for web-based or mobile-optimized terminal access as of 2026.** The current Charm lineup (Bubble Tea, Lip Gloss, Bubbles, Glamour, Wish, Harmonica, Log, plus apps Crush/Glow/Mods/Gum/Skate) has no web terminal, browser client, or dedicated mobile app.

**The most relevant data point is what Charm's own Crush does for remote access, and it's not Wish.** `crush serve` runs a client-server mode: multiple TUI clients connect to one shared backend process over **HTTP/SSE**, sharing session lists, message history, permissions, LSP, and MCP state. A workspace stays alive as long as at least one client has an SSE stream open. This is explicitly not SSH-based — Crush expects to be run inside an existing SSH session for remote use (it emits OSC notifications over SSH when supported) rather than shipping its own Wish-based server. Android is listed as a supported "platform" in the sense of running a terminal emulator + SSH client, not a native app.

**Alternatives to Wish for serving over SSH:** `gliderlabs/ssh` directly (still pre-1.0 by its own roadmap; buys you transport/pty plumbing without Wish's SCP middleware or its 2026 CVEs, but you hand-wire the `tea.Program`-per-session logic Wish already provides safely) or raw `x/crypto/ssh` (full control, you own the exact layer where the pre-auth DoS CVEs live).

**Non-SSH options:** ttyd (actively maintained, WebSocket + xterm.js, full terminal emulation including Sixel/ZMODEM) beats GoTTY, its Go predecessor, now in maintenance mode. Mosh (UDP-based, survives IP roaming and connection drops between wifi and cellular) is a transport-layer improvement that sits in front of an SSH session, not a replacement for it — needs an open UDP port range and doesn't preserve scrollback on its own, so pair with tmux.

**Practical paths, from least to most commitment:**

1. **Run the CLI wherever it already lives, connect via a standard mobile SSH client** (Termius, Blink Shell), paired with tmux for persistence and optionally Mosh for cellular resilience. Zero new code, smallest new attack surface — reuses `sshd` rather than standing up a purpose-built server.
2. **Embed Wish** if the goal is literally "SSH into this exact TUI as-is," accepting that this makes you the operator of internet-facing SSH infrastructure with an ongoing patch-tracking obligation (pin v2.0.3+, public-key auth only).
3. **Decouple the agent core from the renderer and expose it over HTTP/SSE**, the Crush model, letting the TUI be one client among several. More upfront engineering, but the only option that also opens a path to a real mobile-native UI later rather than "a terminal emulator on a phone." Only worth pursuing once an actual second client would use the API, not speculatively.

Mouse/resize/rendering fidelity over SSH from a mobile client couldn't be confirmed against current sources this session (search budget exhausted) — flagged `[unverified]`, worth a manual pass against Termius/Blink Shell specifically before relying on it, rather than assuming desktop-SSH parity.

## Recommendation: Bubble Tea or alternative

**Use Bubble Tea.** For a single-user Go coding-agent CLI that needs to eventually support remote/mobile access, nothing in this research surfaces a reason to deviate from it.

The case is cumulative, not any single fact:

- The ecosystem is actively maintained through August 2026 with no credible evidence of the organizational distress sometimes attached to Charm's name from 2024 — release cadence across all five core libraries is unbroken, and the org shipped a new flagship product (Crush) in the same window.
- The hardest problems this project will hit — token streaming, syntax-highlighted diffs, unbounded scrollback, split layout, mouse hit-testing, resize propagation, goroutine-safe async updates — all have a working, production-scale reference implementation to copy from directly: Crush's source. That's a materially stronger starting position than any alternative here offers, where the best available reference (Ratatui/Codex) is a different language and the others (tview, gocui, termui, Textual) have no comparable coding-agent-scale example at all.
- Crush's architecture doc is itself a warning worth heeding on day one: don't default to deep nested `tea.Model` composition. Start with something closer to Crush's flat single-model, imperative-sub-component, capability-interface pattern, and budget real engineering time for layout and testing since Bubble Tea provides neither out of the box (`bubblelayout` and `teatest` both have documented gaps, and the community has open, unresolved proposals asking Charm to formalize both).
- tview is the only Go alternative worth naming, and only as a fallback if Bubble Tea's architecture becomes a demonstrated blocker — it trades a proven message-passing pattern for a richer stock widget set, which is not a clear win for a team with no existing blocker.
- Switching languages entirely (Rust/Ratatui, Python/Textual, Node/Ink) is not a velocity or capability unlock for the TUI layer specifically, and it is a real cost for the project as a whole: it either forces a full core rewrite (plausible only for Rust, given static-binary parity with Go) or introduces a subprocess/FFI boundary that OpenAI's own Codex migration argues against for exactly this class of application. Ink in particular is documented as the wrong choice for a token-streaming workload — it's the reason both Claude Code and Codex have each moved off stock Ink.
- For remote/mobile access, don't reach for Wish as the first move despite it being the "obvious" Charm-native answer. Its 2026 CVE history (one CVSS 9.6, one CVSS 7.5) makes it a standing security-maintenance obligation, not a one-time integration. Start with tmux + a mobile SSH client (zero new code), and only build toward Crush's `crush serve` HTTP/SSE client-server model if remote/mobile becomes a first-class, recurring workflow rather than an occasional convenience.
