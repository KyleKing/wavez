# Mobile delivery options for a personal coding-agent companion app

Researched 2026-08-12. Scope: a solo developer building a personal app to remotely monitor and approve/deny actions from a coding agent running on their Mac. Push notifications are a hard requirement. May or may not ever go on the App Store.

## Path 1: Native iOS (Swift/SwiftUI)

**Effort, basic app (view status, approve/deny, receive push):** 3-5 developer-days. SwiftUI makes a list/detail status screen and an approve/deny action view fast to build (roughly 1-2 days). APNs integration for a single personal device is the well-trodden path on this platform: register for remote notifications, get a device token, and push from your own backend or a small server relay — this is the reference implementation Apple designs around, so it has the least incidental friction of any path here (1 day, mostly boilerplate plus a `.p8` key or certificate). The remainder is wiring the UI to the token-approval flow and testing on-device.

**Distribution without going through the App Store:**
- **Xcode free/personal-team provisioning**: you can build and install onto your own iPhone from Xcode with a personal-team (free) Apple ID, no paid Developer Program membership required. The catch: the resulting provisioning profile expires after **7 days**, so you must re-connect the phone to your Mac and re-run/re-sign from Xcode weekly, and certain entitlements are restricted under free provisioning — historically including limits on push notification and background-mode entitlements. This makes free provisioning workable for a demo but annoying for a daily-driver app. [Xcode free provisioning docs](https://documentation.xojo.com/versions/2023r2/topics/application_deployment/ios/deploy_to_device_with_free_xcode_provisioning_profile.html), 2026.
- **Paid Apple Developer Program ($99/year, confirmed current as of 2026)**: unlocks full entitlements (push notifications, background modes) and removes the 7-day expiry via proper distribution/ad-hoc provisioning profiles (up to 1 year validity), plus TestFlight. [Apple Developer Program pricing coverage](https://richestsoft.com/blog/apple-developer-program-cost/), 2026; [Apple's own comparison page](https://developer.apple.com/support/compare-memberships/).
- **TestFlight (internal testing)**: with the $99/year membership, internal testers (anyone on your own App Store Connect team, i.e. yourself) get new builds within minutes of upload with **no Beta App Review and no App Store submission**. This is effectively "sideload with proper entitlements and no 7-day expiry, without needing App Store review." Up to 100 internal testers if you ever want to add others. [TestFlight internal vs external testing](https://www.tfinvites.com/blog/internal-vs-external-testflight-testing), 2026.
- **EU DMA alternative marketplaces / sideloading**: as of 2026 this is real (AltStore PAL, Epic Games Store, Onside, etc.) but is gated to devices with an Apple ID registered to an EU country and physically located in the EU — not applicable to a US-based solo developer's own use case. [TechCrunch on alternative EU app stores](https://techcrunch.com/2026/02/22/move-over-apple-meet-the-alternative-app-stores-available-in-the-eu-and-elsewhere/), Feb 2026; [Apple's own DMA impact page](https://www.apple.com/newsroom/2025/09/the-digital-markets-acts-impacts-on-eu-users/).

**Background execution (iOS 18/19, 2026):** iOS remains strict. `BGTaskScheduler` (`BGAppRefreshTaskRequest`, `BGProcessingTaskRequest`) only offers opportunistic, system-scheduled background windows — no guaranteed timers, and processing tasks are capped at roughly 30 seconds of CPU after launch, non-deterministically scheduled based on battery/usage heuristics, and further throttled under Low Power Mode. [iOS background execution limits overview, 2026](https://www.appsonair.com/blogs/background-execution-limits-in-ios-what-every-developer-must-know). **Consequence for this use case: don't rely on background execution to poll the Mac. Use silent/remote push (APNs) as the trigger to wake the app and refresh state — this is the standard, reliable pattern and is well supported.**

**Not achievable / significantly harder:** true continuous background polling or long-running background connections (SSE/websocket held open indefinitely) are not reliable on iOS regardless of framework — push-triggered refresh is the only dependable channel. Free (unpaid) provisioning does not reliably support push entitlements, so for a serious push-notification-dependent app, budget for the $99/year membership.

## Path 2: Cross-platform (React Native / Flutter / Expo)

**Effort, basic app:** 4-7 developer-days if starting from zero framework familiarity; 2-4 days if the developer already knows React (RN/Expo) or Dart (Flutter) reasonably well. The UI work is comparable to native SwiftUI for a screen this simple. The added cost versus native is framework setup, EAS/build-tooling config, and push credential wiring across two native platforms even if you only ship iOS.

**Expo specifics (2026):** `expo-notifications` handles APNs registration and remote push; as of SDK 53+, push notifications are **not available in Expo Go** on Android and a custom **development build** (via `EAS Build`) is required — meaning you can't stay in the pure managed/Expo-Go workflow if you want push, you need to build a dev client. Setup (Firebase/FCM config, APNs key upload to EAS credentials, EAS Build) is documented as roughly 1-2 hours end-to-end once you know the steps. `expo-background-task` exists but, like native `BGTaskScheduler`, only gives opportunistic minimum-interval scheduling, not guaranteed timers — same underlying OS limits as Path 1. [Expo push notifications setup docs](https://docs.expo.dev/push-notifications/push-notifications-setup/), 2026; [Expo background task guidance, 2026 summary](https://viprasol.com/blog/react-native-background-tasks/).

**Framework health (2026):** Both RN and Flutter are mature and considered safe long-term choices. Flutter has passed RN in GitHub stars (~102k vs ~92k) and is often cited as ahead on raw rendering performance (Impeller engine, 6-platform reach). React Native leads on ecosystem size, npm weekly downloads (10M+), and native-module/package availability, and just stabilized its "New Architecture." For a solo dev already comfortable with JS/TS, RN+Expo is the pragmatic pick; Flutter is equally viable if the developer prefers Dart or wants best-in-class rendering. [React Native vs Flutter comparison, 2026](https://quashbugs.com/blog/flutter-vs-react-native-statistics); [second comparison](https://dev.to/moniruzzamansaikat/react-native-vs-flutter-in-2026-which-one-should-you-choose-18fg).

**Personal install without App Store friction:** Same underlying mechanism as native — an Expo/RN/Flutter app still compiles to a real iOS binary that needs either Xcode free provisioning (7-day expiry) or a paid Apple Developer account + ad-hoc/TestFlight distribution to live on your phone longer-term. EAS Build can produce an ad-hoc `.ipa` for internal distribution but installing it still goes through Apple's normal device-registration/provisioning rules — cross-platform tooling doesn't bypass Apple's signing requirements. No net win over native here; it's the same $99/year decision.

**Not achievable / harder:** none of the cross-platform layers change the underlying iOS background-execution or provisioning rules — they inherit exactly the same push-triggered-refresh pattern and the same $99/year-for-durable-install tradeoff as native. The extra cost versus native is purely framework learning curve and build-tooling overhead, which only pays off if the developer plans to also target Android or already knows the framework.

## Path 3: PWA / plain web app (Safari, Add to Home Screen)

**Effort, basic app:** 1-2 developer-days. This is by far the fastest: a status page and an approve/deny button hitting your existing tunnel URL is close to what you'd build for a local web dashboard anyway, with no App Store, provisioning, code signing, or build-tooling overhead at all.

**Push notifications on iOS Safari (2026 status):** Apple added Web Push for Home Screen PWAs in **iOS 16.4 (March 2023)**, and it remains supported in 2026 — Safari 18.4 added "Declarative Web Push," a simplified delivery mechanism that doesn't require a service worker for basic notification display. Critically, **the Push API only works for a PWA that has been added to the Home Screen** ("Add to Home Screen") — a page open in a regular Safari tab cannot receive push. As of early 2026, over 95% of iPhones run iOS 16+, so push-capable PWAs are viable for the vast majority of users, non-EU. [PWA iOS push notification status, 2026](https://webscraft.org/blog/pwa-pushspovischennya-na-ios-u-2026-scho-realno-pratsyuye?lang=en); [MagicBell iOS PWA limitations guide, 2026](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide).

**EU caveat [unverified relevance]:** in March 2024 Apple changed EU PWA behavior for DMA compliance, and EU-region PWAs reportedly lost standalone/push support for a period, opening in plain Safari tabs instead. Since the user is presumably US-based this likely doesn't apply, but flag it if the app or Apple ID region ever changes. [DMA PWA impact reporting](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide), 2026.

**Background execution:** essentially none. A backgrounded/closed Safari PWA gets no CPU time; the only way it "does anything" while not open is via push notifications waking a service worker briefly to display a notification. This is actually not a real handicap for this use case, since the native/cross-platform paths are equally push-dependent for anything reliable.

**Not achievable / significantly harder:** rich native UI chrome (haptics, native action buttons on notifications beyond basic actions, Face ID gating, widgets, Live Activities/Dynamic Island) is unavailable or much harder on a PWA. No App Store presence if that's ever wanted later. Notification interactivity is more limited than APNs' native notification actions (e.g., inline "Approve"/"Deny" buttons directly on the lock-screen notification are more mature and reliable via native APNs categories than via Web Push actions on iOS Safari today [unverified — iOS Web Push notification action-button support specifically should be smoke-tested before relying on it]).

## Effort summary

| Path | Basic app (a) | Notable gaps (b) |
|---|---|---|
| Native SwiftUI | 3-5 days | Free provisioning expires weekly and restricts push entitlements; $99/yr needed for a durable, fully-capable build |
| React Native / Flutter / Expo | 4-7 days (2-4 if already fluent) | Same Apple provisioning/push constraints as native, plus framework overhead; no real advantage unless targeting Android too |
| PWA (Add to Home Screen) | 1-2 days | No native notification-action richness, no App Store presence, unverified reliability of inline approve/deny actions in Web Push notifications |

## Recommendation

For a solo developer who wants working push-based monitor/approve-deny for personal use as fast as possible: **build the PWA first.** It is the only path where push notifications, "Add to Home Screen" installability, and a full working app converge inside 1-2 days, with zero App Store friction and zero code-signing/provisioning overhead. iOS's Web Push support for Home Screen PWAs is confirmed live and current (iOS 16.4+, refined through Safari 18.4's Declarative Web Push), and background execution limits are irrelevant here since every path in this comparison is push-driven anyway, not background-polling-driven.

The one thing to verify early, before committing: whether Web Push on iOS Safari supports **actionable notification buttons** (approve/deny directly from the notification, without opening the app) at the fidelity you want — this is well-established for native APNs but I could not confirm current iOS Web Push notification-action-button support with confidence [unverified, smoke-test before relying on it]. If that turns out to be a hard requirement and Web Push falls short, the fallback is native SwiftUI with the $99/year Apple Developer Program and TestFlight internal testing — TestFlight sidesteps App Store review entirely for a solo developer's own builds, giving full entitlements (proper push, no 7-day expiry) at roughly 3-5 days of build effort. Skip the cross-platform frameworks unless there's already a concrete plan to also ship Android or the developer already has deep RN/Flutter fluency — they inherit every iOS constraint the native path has, with none of the offsetting speed advantage the PWA path has.
