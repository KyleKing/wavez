# Audit, 2026-08-18: capabilities, cost, models, hosting, UX

An outside read of wavez against the job it is trying to take over, daily
software engineering on this repo, currently done in Claude Code. Written from
the code and docs in this tree, from three web research passes dated
2026-08-18, and from one short drive of the TUI under tmux. Wall-clock
comparison of `wavez -p` against `claude -p` is deliberately absent: the
machine was running four build lanes while this was written, so any timing
taken here would be wrong. That pass is still owed.

Every number below is labeled **measured** (someone ran it and recorded it),
**estimated** (derived from measured numbers or from source bytes), or
**unverified** (a claim from a source, repeated with its source).

## Verdict

Wavez is roughly one third of a daily driver and the missing third is not the
part the design spends its innovation budget on. The deterministic layer is
real and already better than what Claude Code offers: change-triggered gates,
coverage-selected tests, a fail-to-pass check, a mutation gate, a reachability
check, an abstention rule that makes a check which examined nothing visible.
None of that is reachable daily, because the thing in front of it cannot
reliably land a two-line edit.

Three findings decide the near term.

**The local model is the binding constraint and no drop-in replacement exists.**
qwen3:8b lands 2 of 10 edits by strict spec reading. The August 2026 research
turned up exactly two other models that fit ~10 GB with confirmed llama.cpp
tool-call support (Nemotron-Nano-9B-v2 at 6.53 GB, Qwen3.5-9B at ~6.6 GB), and
Qwen3.5-9B has an open bug for the exact failure that matters
([llama.cpp#20837](https://github.com/ggml-org/llama.cpp/issues/20837), tool
calls emitted as XML mid-thinking-block). Nobody has published a harness-grade
benchmark of the 8-14 B tier at all. So "swap the model" is a probe to run, not
a plan to rely on.

**A run in this worktree fails before its first turn, silently.** Measured
today: `wavez -p` in a git worktree of the jj-colocated repo exits with
`capturing checkpoint: … is not a jj repository`, and the same failure through
the TUI leaves the thread at `○ idle` with an empty transcript, no error row,
and nothing in the daemon log. `mt.lastErr` is stored in
`internal/daemon/manager.go:433` and never appears on `api.ThreadInfo`. That is
a P0 and it is cheap.

**The M4 Pro is the highest-leverage unbuilt thing in the whole audit.** A
Qwen3-Coder-30B-A3B or Devstral-Small-2 served from the 24 GB laptop changes
the model tier from "2/10 edits" to something in the range the harness-bench
run measured for that class (80% task pass over 16 real SWE tasks, unverified
for these exact models), at 3 B active parameters and therefore fast. What
stands between here and there is about fifty lines: `internal/runtime`
hardcodes `127.0.0.1` in three places and `internal/config` exposes a port and
no host. Section 3b names each one.

Ranked shortest path, argued in section 5: surface the run error, wire the
remote endpoint and probe the M4 Pro, raise the local served window off 8k,
parse llama-server's `timings` block, then decide whether hosted-by-default is
honest for this repo.

## 1. Capability gap against Claude Code

Ranked by how much each blocks daily software engineering on this repo. The
column that matters is the last one: a gap the design declined is a different
problem from a gap nobody has built.

| # | Gap | Status | Blocks daily use |
|---|---|---|---|
| 1 | Edit reliability on the local tier (2/10) | Not built past `str_replace` | Total |
| 2 | A run dies invisibly outside a jj repo | Bug | Total, here |
| 3 | Web search and fetch | M3, not built | High |
| 4 | Multi-file planning | Escalates to hosted on file count alone | High |
| 5 | Context gathering breadth (no glob, no ls, no multi-edit) | Not built | Medium-high |
| 6 | Local context window at 8k served | Tuned choice, revisitable | Medium-high |
| 7 | Permissions do not persist past a process | Not built | Medium |
| 8 | Cost and speed visibility reads dashes | Not built (`timings` unparsed) | Medium |
| 9 | Project instructions do not auto-load | **Declined** (DESIGN.md) | Medium |
| 10 | Task tracking / todo list | **Declined** (DESIGN.md) | Medium |
| 11 | Subagents past one level | **Declined** (DESIGN.md) | Low-medium |
| 12 | MCP client | M3, not built (loading up front **declined**) | Low-medium |
| 13 | Hooks: 2 events, not 8 | **Declined until M2** | Low |
| 14 | Resume exists, no "continue latest" | Not built | Low |
| 15 | Images, notifications, mobile | M2 / M4 | Low |

**1. Edit reliability.** DESIGN.md's own measurement: `str_replace` 2/10,
hashline 1/10, on qwen3:8b in a real tool loop over 5 tasks and 20 runs. The
harness-side causes are fixed (`_ai_/bench/dogfood.md` lists five of them, worth
8.6x wall time between them) and what remains is the model producing a verbatim
anchor. Claude Code with Sonnet does not miss this. Everything downstream in
wavez is gated behind it, because a gate that never gets a correct edit to
verify is a gate nobody sees working.

**2. The jj precondition.** Measured above. Two distinct problems sit here: the
hard dependency itself (`internal/agent/loop.go` captures a checkpoint before
turn one, and `git worktree` copies of a jj-colocated repo have no `.jj`), and
the fact that the failure is invisible in every client. The second is the
serious one. See section 4, P0-1.

**3. Web search and fetch.** M3. Every "what changed in this library's API"
question goes back to Claude Code today, and those are a real fraction of daily
work. Nothing in DESIGN.md declines it.

**4. Multi-file planning.** `internal/router/router.go` escalates on
`FileCount > 1` with no further judgment, so any change touching two files is
hosted, always. That is a defensible M1 rule and it means the local tier is
never exercised on the shape it would have to handle for the thesis to pay off.
Claude Code plans across files as a matter of course.

**5. Context gathering.** The tool set is exactly seven: `read`, `write`,
`str_replace`, `shell`, `search`, `context`, `question`
(`internal/tools/`). There is no `glob`, no directory listing, no multi-edit,
and no parallel tool calls. A model that wants to know what is in a directory
must shell out, which pays the guard and the permission gate for a read. The
`context` bundle and `@symbol` expansion are genuinely better than what Claude
Code offers for the first turn (measured: `@looksLikeQuestionToUser` answered
in one turn where search-then-read took three), and they do not cover the
mid-task "list the files under internal/gate" question.

**6. The 8k served window.** `internal/runtime/config.go` serves 8192 tokens and
`internal/router/router.go` escalates above 8000. Estimated from source bytes:
the stable prefix is already 1.7-1.9k tokens before the user says anything (614
bytes of `BaseSystem`, ~7.1 KB of Go source for the seven tools' descriptions
and schemas, taken as ~5.5-6 KB serialized at ~4 chars per token). That is
around 22% of the window spent on prefix, and one `read` of a 300-line Go file
is another 3-4k. Two file reads and the turn escalates. The 16 GB ceiling is
the reason, and it is worth re-measuring: KV cache for qwen3:8b at 16k is not
obviously unaffordable next to a 5 GB model, and the router's escalation
threshold is doing more routing work than the file-count rule is.

**7. Permissions.** `internal/agent/permission.go:24` says it plainly: the
gatekeeper remembers an `AllowAlways` for the lifetime of the process and is not
persisted. Claude Code's settings-level allow rules survive restarts. A daemon
restart re-asks about every `go test` invocation.

**8. Cost and speed visibility.** The diagnostics panel is honest about not
knowing (dashes, not zeros, which is the right call and DESIGN.md argues it
well), and what it does not know is most of the panel. Driven today: `tok/s -`,
`prefix hit -`, `cache read -`, `model - resident`, with a llama-server actually
serving on 8080. The cause is named in DESIGN.md and confirmed in the code:
`internal/llm/openaic/wire.go` parses content, tool calls, and `usage`, and
llama-server's `timings` object (`prompt_per_second`, `predicted_per_second`,
`cache_n`) is dropped on the floor.

**9-13, the declined set.** These are choices, and the audit's job is to say
what each costs rather than to reopen it.

<details>
<summary>What each declined decision costs, with the DESIGN.md line that declines it</summary>

- **Project instructions.** "In the context of project instructions, facing
  auto-loading `AGENTS.md` and `CLAUDE.md` vs explicit opt-in, we list context
  files and sections in `.wavez.pkl`". The cost is already recorded in
  `_ai_/bench/dogfood.md`: the model reached for `//nolint:varcheck` to silence
  a build error, the guidance against that lives in this repo's AGENTS.md, and
  wavez had never read it. The replacement mechanism (a `context` list plus an
  ast-grep rule) worked once it was wired, which is the decision holding up
  rather than failing. The residual cost is a per-repo setup step and a class of
  house-style knowledge that has no rule form.
- **Task tracking.** "we keep both halves in the harness and ship no
  model-authored list … accepting that a long task has no live checklist on
  screen until the schedule view lands". The accepted cost is exactly what shows
  up: on a five-step task there is nothing on screen saying which step is
  running. The Cycles design answers this properly and is M2.
- **Subagents.** "no multi-agent hierarchies past one level of delegation", and
  sub-threads are M2, so today the level count is zero. For this repo's work
  (one repo, one machine) that is a small loss, and it is a large loss for the
  one thing wavez itself does daily, which is running several lanes at once.
- **MCP.** Declined only in the "loaded up front" form. On demand from an
  allowlist is M3. Cost today is any workflow that reaches a service through an
  MCP server.
- **Hooks.** Two events, held until M2, with the reasoning per event spelled out
  (session start is covered by `context`, prompt submit by mention expansion,
  pre-compaction by compaction being deterministic). The argument holds. The one
  candidate the decision itself names, thread-finished, is the one that would be
  used daily, for notification.
- **Plugins, and a git backend beside jj.** Both firmly no. The git decision is
  what produces finding P0-1, and the fix is an error message rather than a
  backend.

</details>

## 2. Where the time goes

### Assumptions

The model below is arithmetic over numbers already in the repo. It assumes: one
edit-shaped turn emits ~190 output tokens (measured, `str_replace` average over
20 runs), local decode at 18-21.5 tok/s with thinking off (measured), prompt
eval on a cache-warm append at ~0.2 s for a 3k prefix (measured), gates on this
repo at the per-edit budget DESIGN.md sets, and hosted round trips at the
`claude -p` figure of 25.8 s per edit writing whole files (measured in
`_ai_/demos/intent-edits/timing`). It does **not** model queueing, a cold model
load (1.6 s to first token, measured), or the coverage map build.

Freshly measured today, incidentally, on this worktree with four lanes
competing: the coverage map build examined 360 tests in **104.4 s**
(`.wavez/gate.log`), against DESIGN.md's 118 s for 356 on a quiet machine. That
is a one-time-per-clone cost and it lands in the background at startup.

### A typical small edit, single file, local tier

| Term | Time | Share | Basis |
|---|---|---|---|
| Prefill, cache-warm append | ~0.2-0.5 s | 2% | measured |
| Turn 1 decode: a `read` call, ~30 tokens | ~1.7 s | 12% | estimated from 18 tok/s |
| `read` execution | ~5 ms | 0% | estimated |
| Turn 2 decode: `str_replace`, ~190 tokens | ~10.6 s | 75% | measured (12.5 s wall) |
| Format pre-pass, in process | ~50 ms | 0% | estimated |
| LSP diagnostics gate, one file | 1.5-5 ms | 0% | measured |
| Selected tests, 12 of 356 | ~1-2 s | 10% | measured selection, estimated runtime |
| **Total** | **~14 s** | | matches the 14 s dogfood run |

Decode is 85-90% of a successful small edit. Nothing else on the list is worth
optimizing until that changes. Multiply by the 2/10 success rate and the real
expected cost of a *landed* small edit is one local attempt plus a hosted one,
because the router escalates after a single failure and never retries local.

### A typical multi-file change

The router sends this hosted on turn one (`FileCount > 1`), so the local tier
never appears. What is left is a hosted latency term plus the local
deterministic layer.

| Term | Time | Basis |
|---|---|---|
| Hosted turn, whole-file output (2-5k tokens) | ~26 s per edit | measured, `claude -p` Sonnet |
| Hosted turn, intent or hole-sized output | 5-8 s projected | DESIGN.md projection, **unverified** |
| Format, convention rules, LSP across 5 files | ~0.2 s | measured (1.18 s worst case at 37 files) |
| Selected tests, importer level | seconds to minutes | measured: 210 of 356 at importer level, 12 at line level |
| Fail-to-pass check | 1.4-1.6 s | measured |
| Diff review, one model read of the diff | one hosted turn | measured 12/12 on rehearsed diffs |
| Mutation gate, if run | 6.35 s per mutant | measured, on demand only |

The interesting term here is test selection, not the model. A multi-file change
that lands at importer level runs 210 tests where line level runs 12. The
coverage map is what closes that gap and it is already built and measured. On a
change touching five files, the difference between a good and a bad selection is
larger than the entire local decode budget of a small edit.

### Which lever moves which term

| Lever | Term it moves | Measured effect | State |
|---|---|---|---|
| Thinking off | Output tokens per turn | 92 tokens to 3 on "OK"; 119 s to 14 s on an edit | Shipped |
| n-gram speculation | Decode rate on copy-heavy output | 20 to 85 tok/s, 88% draft acceptance | Shipped |
| `str_replace` over whole-file | Output tokens per edit | 190 vs 605 tokens, 12.5 vs 37.7 s | Shipped |
| Escalate after one failure | Expected attempts per landed edit | Bounds it at 2 instead of ~5 | Shipped |
| Append-only compaction | Prefill on long threads | Avoids a 5-7x mid-context edit cost | Shipped (minimal) |
| Coverage-map selection | Gate time on multi-file changes | 12 tests vs 210 | Shipped |
| Intent edits + hole fill | Output tokens per change | 161 s to 6.7 s on qwen3:8b, correctness unproven | M3 |
| Modifiers | Output tokens for named refactors | Not yet measured | M3 |
| A stronger model tier | Success rate, therefore attempts | Not yet measured | Section 3 |

Read together: the shipped levers have already taken the local path from ~161 s
to ~14 s per edit attempt, and the remaining local time is decode of 190 tokens
at 18 tok/s. The next order of magnitude does not come from making those 190
tokens faster. It comes from not emitting them (intent edits, Modifiers) or from
emitting them somewhere faster (a remote or hosted tier). That is DESIGN.md's own
conclusion and the arithmetic supports it.

**One conclusion the design has not drawn.** Prompt caching is a much weaker
lever for wavez than for Claude Code, and the reason is a wavez design decision.
The stable prefix is 1.7-1.9k tokens (estimated) because "re-derive over
remember" keeps carried context small. Claude Code's cacheable prefix is an
order of magnitude larger. On the token profile in section 3c, caching takes a
Sonnet day from $1.08 to $0.89, which is 18%, where the same arithmetic on a
20k-prefix agent saves 59%. Caching is worth wiring for correctness of the
numbers, and it is not the cost lever DESIGN.md's model-routing section implies.

## 3. Model and hosting options

Researched 2026-08-18. Every price and size below carries its source. Several
conflict with each other and those are flagged rather than reconciled.

### (a) Local, on the 16 GB M2 Pro, under ~10 GB

The honest answer is that qwen3:8b's position is defensible and the field of
alternatives is thinner than expected.

| Model | Size (Q4_K_M) | Tool calls in llama.cpp | Evidence |
|---|---|---|---|
| Qwen3-8B | 5.03 GB | Yes, native template, `--jinja` | [bartowski GGUF](https://huggingface.co/bartowski/Qwen_Qwen3-8B-GGUF), [Qwen llama.cpp docs](https://qwen.readthedocs.io/en/latest/run_locally/llama.cpp.html) |
| Nemotron-Nano-9B-v2 | 6.53 GB | Yes, `nemotron_h` since llama.cpp b6315 | [HF discussion](https://huggingface.co/nvidia/NVIDIA-Nemotron-Nano-9B-v2/discussions/4) |
| Qwen3.5-9B (Mar 2026) | ~6.6 GB | Yes, with an open bug | [Qwen3.5 blog](https://qwen.ai/blog?id=qwen3.5), [llama.cpp#20837](https://github.com/ggml-org/llama.cpp/issues/20837) |
| Devstral-Small-2507 (24B) | 14.3 GB | Yes | [unsloth GGUF](https://huggingface.co/unsloth/Devstral-Small-2507-GGUF) |

Ruled out on size, confirming DESIGN.md's risk list: Qwen3-Coder has no small
dense variant and never did (official sizes are 480B-A35B, 30B-A3B, and
Qwen3-Coder-Next at 80B/3B active, [QwenLM/Qwen3-Coder](https://github.com/QwenLM/Qwen3-Coder));
GLM-4.5-Air is 106 B total and does not fit at any quant regardless of its 12 B
active count; Nemotron 3 Nano 30B-A3B and Seed-OSS 36B are the same story. An
MoE's active-parameter count sets its speed and its total parameter count sets
its memory, and several 2026 write-ups conflate the two.

Two things changed that DESIGN.md predates. **Gemma 4 shipped 2026-04-02**
([Google](https://blog.google/innovation-and-ai/technology/developers-tools/gemma-4/))
in E2B, E4B, 12B Unified, 26B MoE, and 31B dense, with native tool calling at
every size and a July stealth update that fixed tool-calling bugs. The 12B and
E4B are the ones to size for this laptop and I could not find confirmed GGUF
sizes for either (**unverified**). **Qwen3.5 and Qwen3.6 both exist**, which
makes "qwen3:8b" a two-generation-old choice even if it is still the right one.

The load-bearing benchmark found is
[harness-bench (2026-04-28)](https://neuralnoise.com/2026/harness-bench-wip/),
16 real SWE tasks across five harnesses on an M3 Max, and every model in it is
27 B or larger: Qwen3.6-27B at 82.5%, Gemma-4-31B at 81.2%, Qwen3.6-35B-A3B at
80.0% and roughly twice as fast as the dense 27B, Qwen3-Coder-Next at 70.0%. It
also reports no malformed-JSON or looping failures at all in that sweep, which
cuts against the usual narrative and says nothing about the 8 B tier. Nobody has
published a harness-grade result for 8-14 B dense models. The most recent Aider
polyglot rows for small models are Qwen2.5-Coder generation (14B at 69.2%
correct, 100% correct edit format; 7B at 57.9%, 100% format,
[aider leaderboard](https://aider.chat/docs/leaderboards/edit.html)), which is
stale enough to be a curiosity.

**So: keep qwen3:8b, and probe Nemotron-Nano-9B-v2 and Gemma-4-12B** on the
five-task, 20-run edit harness that produced the 2/10 number, since that is the
only measurement that answers the question for this repo. Devstral-Small-2507 at
14.3 GB is over any reasonable budget on a 16 GB machine that also has to run
`go test`, and it belongs on the M4 Pro instead.

### (b) Self-hosting on the M4 Pro, 24 GB, over the LAN

This is where the interesting models live.

**What fits.** Default Metal wired limit is about 75% of unified memory, so
roughly 18 GB on a 24 GB machine, raisable with
`sudo sysctl iogpu.wired_limit_mb=20480` (resets on reboot, persist in
`/etc/sysctl.conf`, leave 4 GB for macOS).

| Model | Quant | Size | Fits 18-20 GB |
|---|---|---|---|
| Qwen3-Coder-30B-A3B | MLX 4-bit | 17.2 GB | Yes, tight |
| Qwen3-30B-A3B | GGUF Q4_K_M | 18.6 GB | Borderline, little room for KV |
| Devstral-Small-2507 (24B dense) | Q4_K_M | 14.3 GB | Comfortably |
| Mistral-Small-3.2-24B | Q4_K_M | 14.3 GB | Comfortably |
| Qwen3-14B | Q4_K_M | ~9 GB | Easily |
| Seed-OSS 36B | Q4_K_M | 21.8 GB | No |
| GLM-4.5-Air | Q4_K_M | 73.5 GB | No |

**Expected speed.** M4 Pro is 273 GB/s against the M2 Pro's 200 GB/s
([Notebookcheck](https://www.notebookcheck.net/M4-Pro-20-Core-GPU-vs-M2-Max-30-Core-GPU-vs-M4-Max-32-Core-GPU_12870_11572_12884.247598.0.html),
[Apple](https://www.apple.com/newsroom/2023/01/apple-unveils-m2-pro-and-m2-max-next-generation-chips-for-next-level-workflows/)),
so about 1.35x on the same model, and decode is bandwidth-bound. The lever is
not the chip, it is the architecture: a 3 B-active MoE streams 3 B parameters
per token from an 18 GB file, so Qwen3-Coder-30B-A3B on the M4 Pro should decode
in the same range as an 8 B dense model while behaving like a 30 B one. Reported
numbers, all **unverified** and none from a controlled cross-chip run:
Qwen3-Coder-30B-A3B via Ollama on an M4 Pro at
[39.45 tok/s](https://gargashwani.medium.com/i-tested-4-local-coding-models-on-my-m4-pro-one-was-6-7-faster-5257046c2707),
Qwen3-30B-A3B MLX on M4-class silicon at
[45-64 tok/s](https://huggingface.co/posts/wolfram/819510719695955). Against
this laptop's measured 18-21.5 tok/s on an 8 B dense model, that is a 2-3x
decode improvement *and* a model two tiers up.

**What wavez would have to change.** Small and well contained.

- `internal/runtime/supervisor.go:22` and `:27`: `LocalBaseURL` and
  `localHealthURL` build `http://127.0.0.1:%d` from a port. They need a host.
- `internal/runtime/process.go:89`: `buildArgs` passes `--host 127.0.0.1`. Only
  relevant to a server wavez starts, so it stays as is for the local case.
- `internal/runtime/supervisor.go` `Ensure`: the flow is "probe loopback, else
  start a server here". A remote endpoint must probe and stop, never fall
  through to starting a local llama-server, because starting a 6 GB model on the
  16 GB laptop is exactly what pointing at the M4 Pro was meant to avoid.
- `internal/config/pkl/Wavez.pkl`: `localPort` becomes `localBaseURL` (or a
  host beside the port), plus a `localKeyCommand` mirroring `hostedKeyCommand`
  so a bearer token never enters the environment. `internal/config/loader.go:47`
  and `internal/config/config.go:68` follow.
- `internal/app/app.go:348`: already builds the local provider through
  `openaic.WithBaseURL`, and `openaic.WithAPIKeyFunc` already exists for the
  hosted tier, so the client side needs no new machinery.
- `internal/app/app.go:43`: `DefaultLocalBaseURL` is a second hardcoded
  loopback constant and should read from config.
- Memory-aware admission (M2) and the diagnostics memory row currently describe
  *this* laptop's headroom. With a remote model, the headroom that constrains
  the router is on the other machine, and neither the daemon nor the panel has a
  way to know it.

**A probe the owner can run in ten minutes.** Nothing here needs wavez.

<details>
<summary>Step list for probing the M4 Pro</summary>

On the M4 Pro:

```sh
# 1. raise the Metal wired limit for the session
sudo sysctl iogpu.wired_limit_mb=20480

# 2. serve, bound to loopback only, with a key and jinja templating
llama-server -m ~/models/Qwen3-Coder-30B-A3B-Q4_K_M.gguf \
  --host 127.0.0.1 --port 8080 \
  --api-key "$(security find-generic-password -w -s wavez-local)" \
  --jinja --ctx-size 32768 -ngl 999 --spec-type ngram-simple --cache-reuse 256

# 3. expose it on the tailnet only, never on the WiFi
tailscale serve --bg http://127.0.0.1:8080
```

From the M2 Pro:

```sh
curl -s https://<m4-name>.<tailnet>.ts.net/v1/chat/completions \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"model":"local","stream":false,
       "messages":[{"role":"user","content":"Reply with exactly: ok"}]}' \
  | jq .timings
```

The `timings` object carries `cache_n`, `prompt_n`, `prompt_ms`,
`prompt_per_token_ms`, `prompt_per_second`, `predicted_n`, `predicted_ms`,
`predicted_per_token_ms`, `predicted_per_second`
([server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)).
`predicted_per_second` is the decode number to compare against this laptop's
18-21.5 tok/s, and `prompt_per_second` is the one that decides whether a LAN
round trip on a 6k-token prompt is tolerable. Two readings of that README
disagreed on whether streaming needs `"timings_per_token": true`, so use
`"stream": false` for the probe. For a controlled comparison rather than a
single request, `llama-bench -m model.gguf -p 512 -n 128 -r 5 -ngl 999`.

Then repeat the five-task, 20-run edit harness that produced the 2/10 number
against the remote endpoint. That is the number that decides everything.

</details>

**Security.** Do not bind to `0.0.0.0`. Bind loopback and let `tailscale serve`
carry it, so nothing on the home WiFi can reach the port at all and device
identity is per-connection rather than one static shared key. The record for the
other approach is bad: Ollama's
[CVE-2024-37032](https://www.wiz.io/blog/probllama-ollama-vulnerability-cve-2024-37032)
was unauthenticated path traversal to root RCE, Ollama ships no auth and PRs
adding it have been rejected or stalled, and scans in 2026 found between
[12,269](https://blog.leakix.net/2026/02/ollama-exposed/) and
[175,000](https://thehackernews.com/2026/01/researchers-find-175000-publicly.html)
wide-open instances depending on method. llama.cpp's own recent
[CVE-2026-34159](https://www.sentinelone.com/vulnerability-database/cve-2026-34159/)
is in the optional RPC backend rather than `llama-server`, so it does not apply
unless distributed inference is enabled, and it is a reminder that the surface
is C++ parsing attacker-controlled bytes. `llama-server` does support
`--api-key` and, contrary to a common claim, native TLS via `--ssl-key-file`
and `--ssl-cert-file`, and Tailscale terminating TLS with its own certs avoids
managing them. Scope a tailnet ACL to those two devices on that port.

The second-order point: an inference server reachable from another device is a
prompt-injection amplifier for an agent that can run shell commands. The
Seatbelt profile and the destructive-command guard are what stand behind it and
they are already the right shape.

### (d) Anthropic direct with caching, versus OpenRouter

Anthropic's current published caching mechanics: 5-minute cache write at 1.25x
base input, 1-hour write at 2x, cache read at 0.1x, `cache_control:
{"type":"ephemeral"}` with `"ttl":"1h"` for the longer option, minimum cacheable
prefix 1024 tokens on Sonnet 5 and 4096 on Haiku 4.5. Batch API is 50% off both
directions and stacks with caching. Sonnet 5's $2/$10 is now confirmed permanent
rather than introductory.

Two things follow for wavez.

**The minimum cacheable prefix is a real constraint here.** Sonnet 5 needs 1024
tokens and Haiku 4.5 needs 4096. Wavez's stable prefix is an estimated 1.7-1.9k
tokens, so it caches on Sonnet and **does not reach Haiku's minimum at all**
unless a project `context` list pushes it there. That inverts the obvious
cost intuition: the cheap Claude model is the one that cannot cache wavez's
prefix.

**OpenRouter is good enough and direct is not worth it yet.** OpenRouter does
forward `cache_control` for Claude models with the 5m default and 1h opt-in
([OpenRouter caching docs](https://openrouter.ai/docs/guides/best-practices/prompt-caching)),
and implicit caching works for OpenAI, DeepSeek, and Gemini through sticky
routing. Pinning a provider is `order: ["<slug>"]` with
`allow_fallbacks: false`
([provider selection](https://openrouter.ai/docs/guides/routing/provider-selection)).
So DESIGN.md's note that Anthropic caching "requires the native wire format and
a pinned provider" is half right: the pinned provider part is right, and the
native wire format is not required through OpenRouter. What *is* confirmed is
that Anthropic's own OpenAI-compatible shim does not honour `cache_control`, so
a second OpenAI-compatible client pointed at Anthropic directly would get no
caching. Given that section 2 shows caching worth about 18% on wavez's token
shape, and that the whole hosted tier costs under a dollar a day, a native
Anthropic client is not worth building. Revisit if wavez ever runs
hosted-by-default.

### Recommendation matrix

Usable today means "would land the work without babysitting". Worth wiring means
the change is bounded and the evidence supports it.

| Task shape | Usable today | Worth wiring next | Not worth it |
|---|---|---|---|
| Small edit, one file | Local qwen3:8b at 2/10, so no. gpt-5-mini escalation, yes | M4 Pro remote tier (Qwen3-Coder-30B-A3B), then re-measure the 5-task harness | A bigger local model on this laptop |

| Question about the repo | Local plus `context` and `@symbol`, genuinely good | Web search for anything outside the repo | Nothing |

The single sentence version: **local is already the right tier for reading and
judging, and it is the wrong tier for writing, and the M4 Pro is the cheapest
way to find out whether that is a property of 8 B models or of local inference.**

## 4. TUI critique

Method: `/tmp/wz-audit/wavez` built from `lane/audit` at 670f100, driven under
tmux at 120x40, 80x24, and 60x18, plus a `NO_COLOR=1` run at 80x24. States seen:
Home empty, Home with one thread, new-thread form, thread view, inbox empty,
diagnostics, palette, help, below-minimum. One model run attempted. Severity is
P0 (blocks the task) through P3 (polish).

**Design specificity.** The information architecture is authored for this
domain and the rendering is not yet. Home's columns (glyph, thread, step in
words, age, spend), the inbox as a fleet-wide queue, and a diagnostics panel
that names its own unmeasured gauges are all specific to running agents and
could not be lifted from a generic list TUI. What renders today is a single
bordered box that shrinks to its content, which is a list widget, not the
lazygit-shaped persistent multi-panel dashboard DESIGN.md describes.

### Health score: 22/36

| # | Heuristic | Score | Key finding |
|---|---|---|---|
| 1 | Visibility of system status | 1 | A run that fails before turn one shows nothing anywhere |
| 2 | Match to the real world | 3 | Domain language throughout (thread, gate, ledger, route), no raw flags |
| 3 | User control and freedom | 3 | Esc reliably goes up one level and never quits, confirmed on every screen |
| 4 | Consistency and standards | 3 | `i`, `D`, `?`, `:` work from everywhere; focus decides verb-vs-character as designed |
| 5 | Error prevention | 3 | Undo requires confirmation, permission gate defaults to ask, guard is fail-closed |
| 6 | Recognition over recall | 3 | Footer hints on every screen, `?` everywhere, palette lists verbs |
| 7 | Flexibility and efficiency | 2 | Palette and vim layers are there; no counts, no batch, no `[`/`]` payoff with one thread |
| 8 | Aesthetic and minimalist | 2 | Frames never fill the terminal, so a dashboard is a 4-line box in 40 rows |

Cognitive load: **low**. Single focus per screen, groups under four items,
progressive disclosure through `?` and the palette. The one failure is working
memory, because a thread's failure state is not on screen and has to be
remembered from elsewhere.

### Priority issues

**P0-1. A failed run is invisible.** Creating a thread whose first turn cannot
start leaves Home showing `○` idle, an empty `step` column, and a thread view
with an empty transcript. Confirmed cause, not a guess: `manager.runTurn`
assigns `mt.lastErr = err` at `internal/daemon/manager.go:433`, and
`api.ThreadInfo` (`internal/api/protocol.go:113`) has no error field, so no
client can render it. Reproduced by running in a git worktree with no `.jj`,
where `wavez -p` prints `capturing checkpoint: … is not a jj repository, fix
with "jj git init --colocate"` and the TUI prints nothing at all. Fix: add an
error to `ThreadInfo`, render it on the Home row and as a transcript row, and
set `event.StateFailed` so the glyph turns `✖`.

**P0-2. The jj precondition is not discoverable before it bites.** The CLI
message is good and arrives after a thread has been created. Nothing at startup
says the project root is unusable. Fix: check for a jj repo when the daemon
resolves the root (`internal/app/app.go` around root resolution) and refuse to
serve threads for it with the same message, or capture the checkpoint lazily so
a read-only thread still works.

**P1-1. Frames do not use the terminal's height.** `frame` in
`internal/tui/frame.go:15` takes width and body lines and emits exactly
`len(body) + 2` rows. Only the thread view consults `m.height`
(`internal/tui/thread.go:392`). At 120x40 Home occupies four rows and 36 are
blank. The consequence is not cosmetic: DESIGN.md's Home carries a fleet
grouped by directory with inline expansion, and there is currently no visible
signal about how much of the screen is available for it. Fix: pad the body to
`m.height - 2` in `frame`, and give Home a scroll region.

**P1-2. The diagnostics strip is the first thing truncated at the minimum
supported width.** At 80x24 the header reads
`wavez · /Users/kyleking/Developer/kyleking/wavez-lane-audit · 1 threads · m…`.
Cause: `internal/tui/home.go:237` formats the title with `m.dir`, the full
absolute path, ahead of `diagStrip`, and `rule` truncates from the tail
(`internal/tui/frame.go:43`). The memory gauge is a headline feature of the
dashboard thesis and it is the piece that disappears. Fix: render the directory
home-relative or as a basename (DESIGN.md's own mock says `~/dev`), and drop
title segments by priority the way `footerHints` already drops footer segments.

**P1-3. The directory group header repeats the absolute path.** `home.go:249`
renders `t.Dir + "/"`, giving
`/Users/kyleking/Developer/kyleking/wavez-lane-audit/` as a group heading
directly under a title containing the same string. DESIGN.md's mock shows
`calcipy/`. Fix: basename, or path relative to the scope root.

**P2-1. The new-thread form collects only a prompt.** DESIGN.md specifies
prompt, directory set, model override, and optional parent. `api.Command`
already carries `Dirs`, `Model`, and `Parent` and `internal/tui/bridge.go:186`
already sends them, so the form at `internal/tui/newthread.go` is the only
missing piece. Choosing the tier at thread creation is the natural place for it,
and today it requires creating the thread and then pressing `m`.

**P2-2. Allow-always does not survive a daemon restart.** Documented at
`internal/agent/permission.go:24`. Every restart re-asks about the same
`go test`. Persisting per-project keys into `.wavez/` would be a small change
and it widens what a compromised run can do without asking, so it deserves an
explicit decision rather than a quiet fix.

**P3-1. `1 threads`.** `home.go:237` uses `%d threads` unpluralized.

**P3-2. The below-minimum message clips at the width it is complaining about.**
`tooSmall` (`internal/tui/view.go:53`) returns one unwrapped line, so at 60x18
it renders `wavez needs at least 80x24 to render (currently 60x18). Resi`.
Wrap it.

## 5. Recommendations

Ordered by ratio of daily-use unblocked to work required. Each names its
evidence, what would verify it, and the DESIGN.md decision it touches.

**1. Surface a run's error in every client.** Evidence: P0-1 above, reproduced
today. Verify: create a thread in a directory with no `.jj` and see a `✖` row
naming the reason. Revisits no decision, and it is a precondition for trusting
any measurement taken through the TUI.

**2. Decide what happens outside a jj repo.** Evidence: this worktree, and every
other lane worktree, cannot run wavez at all. Verify: `wavez -p` completes a
read-only prompt in a plain git checkout. Touches the jj-alone decision, and not
in the way that decision defends: the argument for jj is checkpointing, and a
plan thread or a question thread has nothing to checkpoint. Making capture lazy
keeps the decision intact and removes the precondition.

**3. Point the local tier at the M4 Pro and re-run the edit harness.** Evidence:
Qwen3-Coder-30B-A3B fits 17.2 GB of the M4 Pro's ~18-20 GB usable, its 3 B
active parameters put decode in the same range as an 8 B dense model on 273
GB/s, and its class scored 70-82% on 16 real SWE tasks where nothing that fits
this laptop has ever been measured. Verify: the probe in section 3b, then the
five-task, 20-run harness that produced 2/10, against the remote endpoint. Work:
a host in config, three call sites in `internal/runtime`, and a rule that a
remote endpoint never falls through to starting a local server. Touches the
16 GB local-first decision, which was written for one machine and now has two.

**4. Parse llama-server's `timings` block.** Evidence: five gauges in the
diagnostics panel read as dashes today, `tok/s` and `prefix hit` among them, and
DESIGN.md already names this as the reason. Verify: drive the panel with a live
server and read a number. This is also the instrument recommendation 3 is
measured with, so it comes before the timed comparison the owner still owes.
Touches nothing, it is the honest-gauge decision being finished.

**5. Raise the served window and re-derive the routing threshold.** Evidence:
an estimated 1.7-1.9k-token stable prefix against an 8k window, one file read
consuming another 3-4k, and a router that escalates above 8000 tokens, which
means routing is decided by the served-window choice rather than by task shape.
Verify: measure KV memory at 16k and 32k with qwen3:8b loaded, against the
admission threshold and a running `go test`. Touches the "served context is a
tuned number" line in Model routing, which invites exactly this.

**6. Ship Modifiers for Go before intent edits.** Evidence: section 2's lever
table. Rename, move, and extract are the changes where the model emits a dozen
tokens instead of 190, the backends already exist (`gopls` through the LSP pool
the diagnostics gate already drives), and unlike intent edits there is no open
question about hole-fill correctness. Intent edits are the larger bet and they
carry an unresolved measurement (a 3-line loop right, URL edge cases wrong).
Verify: the same edit harness, counting the share of the final diff produced by
a modifier. Touches no decision, it advances M3's order.

**7. Add web search and fetch.** Evidence: capability gap #3. It is the one
missing capability with no wavez-shaped replacement, since gates and the store
answer only questions about this repo. Verify: a thread that answers a
"what changed in this library" question without leaving wavez. Touches nothing,
it is M3 as planned, and it deserves to move up.

**8. Leave Anthropic-direct alone.** Evidence: section 3d. Caching is worth
about 18% on wavez's token shape because the stable prefix is deliberately
small, the whole hosted tier costs under a dollar a day, OpenRouter forwards
`cache_control` anyway, and Haiku's 4096-token minimum prefix is above what
wavez sends. Revisit only if wavez runs hosted-by-default, which would itself
revisit the local-first decision.
